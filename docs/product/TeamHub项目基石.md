## 1. 当前项目框架与关键概念

### 1.1 项目目的

**已确认：** 面向电力行业技术文档和过程资料，降低发现、获取和版本辨识的成本。个人首先获得日常整理与回找的便利，再通过主动共享和共同补充标签，为组织留下可持续获取的资料资产，减少组织对特定个人持有文件和记忆位置的依赖。

**2026-10-22 明确主次：** AI 最关键的价值是准确找回用户需要的资料、正确版本及可核对位置。整理、资料卡和 Skill 为检索提供底稿和方法；生成简卡、增加标签或完成一次整理不是最终成功标准。

组织积累、培训、新人接手和长期成长是希望支持的结果。初版先解决可获得性和版本可辨识性，不能仅凭文件量增加宣称实现了知识传承。

### 1.2 产品定位

个人日常资料管理与组织共享结合，但两者具有独立的存储和生命周期：

- 个人可以在本地整理、查找、使用资料，不以公开资料或连接共享服务为前提。
- 文件默认私有；适合共享的内容由用户主动发布到组织共享空间。
- 其他成员按权限发现、取回资料，补充共享标签并提交有记录的新版本。
- 本地删除、移动和改名不能支配组织共享资料的存续。
- 标签允许不同人沿自己的线索找到同一份资料，不要求先理解同一套目录分类。
- 资料既可供获授权成员主动查找，也可由发送者通过独立“资料投递”送到指定成员的收件箱，减少接收者主动寻找的成本。

### 1.3 对象、集合与位置

| 概念 | 本项目中的含义 | 关键边界 |
| --- | --- | --- |
| 资料对象 | 持续被查找、整理、收藏和维护的一份资料，可以是文件、压缩包或整套文件夹 | 身份不依赖当前名称、路径或哈希 |
| 整体文件夹资料 | 将一套文件及其内部目录作为一个资料对象管理 | 整体保存版本、发布和更新，初版不拆成内部逐文件协作 |
| 分类文件夹 | 汇集某类已整理资料的导航入口，例如某项目或某类业务 | 与整体文件夹资料不同；当前对应库内实际分类目录 |
| 全部资料 | 本地已整理资料的总览集合 | 包含已归类与未归类资料，不是全部磁盘文件或全部收录状态 |
| 收藏 | 指向特定资料的个人快捷引用 | 不产生副本，不改变整理状态和分类 |
| 待整理区 | 资料已登记但尚待补充整理信息的区域 | 待整理不等于系统不知道这份资料 |
| 文件库路径 | 已整理工作资料及数据库、版本等系统数据所在的物理根目录 | 不等同于“全部资料”这个视图 |
| 组织共享库 | 服务器独立保存和管理的共享资料集合 | 不依赖上传者电脑持续在线 |
| 资料投递 | 将确定内容发送给指定成员并形成接收记录的独立功能 | 提醒不等于本地收录；只获得投递附件不等于获得源资料全部权限 |

分类文件夹概括一批资料，属于更上层的组织单位；这不意味着它比标签更优先。分类与收藏是已整理集合上的入口，标签仍是跨分类、多维查找的主要方式。

### 1.4 当前核心边界

| 事项 | 当前决定 |
| --- | --- |
| 用户与推进 | 首批约 10 人，先本机再内网；不是长期容量承诺 |
| 整理与查找 | 标签表达多维关系、文件夹提供辅助入口；名称、原文及 AI 线索共同服务准确回找，找到可辨认候选集合即可 |
| 导航 | 全部资料总览、文件夹分类入口、收藏直达入口 |
| 收录 | 桌面拖拽进入待整理采用移动源文件，收录时登记身份、区域归属与位置 |
| 状态 | 归类、移出分类、收藏及取消收藏不改变已整理状态 |
| AI 整理方向 | 待整理中后台预处理，用户确认后进入文档库；AI 预整理状态不改变资料归属，见 §4.9（已实施并通过隔离工程验收） |
| 索引与理解 | 快速整理、深入建档两档预处理共用尽可能完整的基础索引；专题分析是独立任务；整理完成不等于正文或图像覆盖完整，见 §10.9 |
| 存储 | 文件库和待整理区可独立或互相包含，不能同路径或嵌入整体资料内部 |
| 共享 | 默认私有、主动发布；共享副本独立持有，个人删除不能连带删除 |
| 可见范围 | 支持指定一个或多个成员；组织管理员不默认读取定向共享或投递内容 |
| 投递 | 独立收发件入口，接收者收到提醒后自主取用；允许发送者撤回，已保存副本不远程删除 |
| 版本 | 两端独立编号；恢复切换已有版本，接收云端不同内容新增本地版本；哈希不替代身份与来源 |
| 治理 | 自由添加标签仍保护贡献；共享永久删除受组织管理员权限控制 |
| 暂不扩展 | 双标签、具体激励算法、审批生效关系、逐文件协作与自动合并等见 §10.4 |

## 2. 为什么需要这个项目

### 2.1 行业工作背景

**问题陈述：** 发起人在电力行业工作，日常存在大量技术文档，也持续产生大量过程资料。现状包括：

1. 资料零散分布在不同人员和设备上，缺少统一、持续的归档方式。
2. 同一主题可能有多个文件或版本，缺少清晰的版本管理手段。
3. 有时不知道资料是否存在、由谁持有；有时知道持有人，但需要反复索取。
4. 工作过程中产生的资料同样缺少整理、分享和持续保留的渠道。
5. 组织培训、人员交接、成果复用与长期积累受到影响。
6. 人与组织之间形成较强的资料依赖：某个人不在，资料的获取和使用就受到影响。

本次讨论没有把所有困难归因于软件缺失。资料维护动力、共享意愿、组织权责和使用习惯同样影响结果。

### 2.2 当前最主要的痛点

发起人明确指出，当前主要卡在：

- **拿不到资料：** 不知道哪里有，或知道但获取成本高。
- **无法确定该用哪个版本：** 缺少明确的版本辨识和历史追溯。
- **实体资料与使用者之间的关系断链：** 资料实体存在，但使用者没有渠道得知它的存在。

“原作者没有写下来的经验和判断”也可能影响知识传承，但本次没有将其提升为初版核心范围。项目先处理可以通过资料管理直接改善的问题。

### 2.3 现有网盘为什么没有充分解决问题

团队尝试过网盘。发起人观察到的主要障碍不是文件没有保存下来，而是使用者难以沿着原来的分类路径找到它。

| 障碍 | 具体表现 | 结果 |
| --- | --- | --- |
| 分类维度单一 | 以文件夹路径表达主要归属，难以同时表达项目、设备、业务等关系 | 不同使用者需要先理解归档者的思路 |
| 分类原则依赖少数人 | 建立目录的人理解当时的分类依据，其他人未必知道 | 直接问人可能比自己查找更快 |
| 层级越来越深 | 新资料不断增加，目录持续细分 | 文件被埋在很深的路径中，获取成本上升 |
| 一份资料有多种用途 | 同一资料可能在多种工作场景中被需要 | 单一路径难以覆盖不同查找习惯 |

讨论中进一步提出的**可能问题**包括重复存放造成版本分叉、上传者不知该放哪里、人员或业务变化后原分类失效。这些是需要观察的推论，不应伪装成已完成的调研结论。

### 2.4 真实需求与方案必要性分别判断

已有工作经验支持这些痛点是真实的，但还不能据此证明：

- 自由标签一定是所有场景中的最优解。
- 必须完全自研，既有产品或流程调整一定无法满足需求。
- 增加标签一定使查找变快。
- 组织希望积累资料，就意味着员工会持续贡献。

项目目前选择推进自由标签与个人、团队结合为系统的主方向，同时将传统文件夹分类与收藏作为辅助的组织和回找方式，让使用者有更好的体验，其必要性和效果需要通过真实任务验证。已有代码、已经投入的时间和功能数量，都不能单独构成继续扩张项目的理由。

## 3. 价值、使用者与合作原则

### 3.1 个人与组织需要同时受益

| 参与者 | 希望获得的直接价值 | 需要警惕的情况 |
| --- | --- | --- |
| 个人资料使用者 | 更容易整理、再次找到自己的资料，也能获取他人的资料 | 系统变成额外填写任务，日常仍回到旧方式 |
| 资料共享者 | 有价值的成果被使用，减少重复找文件和发送资料的劳动 | 共享成本高、边界不清，不愿发布 |
| 后续标签贡献者 | 按自己的工作思路留下入口，同时可能帮助其他人 | 补充动作被多重选择打断，投入大于感知收益 |
| 组织 | 资料持续保留，人员变化后仍可获取，支持交接、培训与复用 | 存了大量文件，却依旧只有少数人知道如何找到 |

**工作假设：** 当个人日常管理获得实际帮助，且共享与后续整理成本足够低时，个人行为有机会持续形成组织资料积累。

“系统成为用户的伙伴”是发起人提出的体验方向，含义是持续提供帮助、带来可感知价值。它是希望形成的使用关系，不替代对具体收益的验证。

### 3.2 项目的判断标准

评估功能时首先考虑：

1. 是否降低了发现、获取或辨识资料的成本。
2. 是否让非原始整理者也能使用已有成果。
3. 是否要求用户承担难以持续的整理成本。
4. 是否损害已共享资料的可用性、可靠性或边界清晰度。
5. 是否服务当前约 10 人的真实工作，而非提前覆盖所有未来情形。

标签数量、文件总量、功能页数量和技术复杂度都不能单独证明价值。

### 3.3 合作方式

以下是发起人明确要求长期遵守的原则：

- 客观、公正，围绕事实与推理讨论；不为取得认同而附和。
- 有理由时直接指出错误、冲突和不合适的假设，并说明原因。
- 区分事实、经验、假设、建议与已确认决策，允许结论随证据改变。
- 日常交流聚焦、简洁，每次优先推进一个问题。
- 先理解项目价值和边界，再讨论实现；未经新的任务授权，不因讨论自然延伸就开始编辑代码。
- 书面基石需要完整、细致、可追溯；详细文档不改变日常交流保持简洁的要求。

## 4. 标签、导航与资料整理

### 4.1 共同语言与不同视角并存

**问题陈述：** 行业内的使用者有理解差异，但并非毫无共同基础。设备、项目、业务、部门等是较有共识的工作线索。

**已确认：** 利用共同语言建立可被他人理解的入口，同时允许个人按工作需要补充关系。初版不要求所有资料服从预先固定、完整的分类体系。上述名称是例子，不是必填字段或强制标签层级。

### 4.2 典型协同场景

1. A 将文件 X 纳入 TeamHub，按设备、部门、类型等思路添加标签，并主动发布资料及随行标签。
2. B 根据部门、名称等自己掌握的线索搜索，在约 10 份候选中认出并取用 X。
3. B 在共享资料上按自己的思路补充两个标签，为后续查找增加入口。
4. C 组合利用 A、B 的标注，找到同一份共享资料。

初次整理可以是专门动作，后续补充希望融入使用过程。“补充共享标签”发生在共享资料对象上；只修改下载后私人副本的标签，不会自动改变共享标注，见 §6.2。

**有条件探索：** 利用标签共现关系提供低成本联想，显著增加复杂度时不为此扩展推荐算法。已有基础联想能力属于工程现状，实际帮助程度仍需验证。

### 4.3 两种不同的“增加”和“收敛”

| 过程 | 发生了什么 | 预期价值 |
| --- | --- | --- |
| 资料积累标签 | 多人给同一资料补充描述关系 | 增加不同使用者发现它的机会 |
| 查询增加条件 | 使用者逐步选择标签或线索 | 缩小候选集合，便于辨认目标 |

覆盖人群从 40% 到 70%、再到 90% 是发起人解释普适性的例子，不是测得的数据或承诺。更多标签也可能带来歧义，数量不能代替效果。

### 4.4 找到文件就是成功

**已确认：** 用尽可能少的操作，让目标进入容易辨认的候选集合，不追求每次唯一命中。约 10 份候选是经验示例，不是固定阈值。

名称和标签是可独立使用的入口。标签承担多维关系表达，不意味着记得文件名的人必须先选标签。二者可以在检索设计中配合；页面是否支持同时叠加以使用指引和契约为准，不能把方向当成每个页面已实现的行为。

按多个标签同时筛选时，目标缺少某个标注也可能被排除。结果减少不一定更成功。文件名、摘要或预览可以辅助辨认，但本原则不自动扩大预览等功能范围。

### 4.5 灵活性与后续收敛

**已确认：** 初版保留自由标签的灵活性，追求普适性而非完美分类。后续依据真实歧义、重复和检索障碍，再决定如何纠错、合并或建立同义关系。

现有基础标签维护工具不等于采用完整治理架构。初版不提前引入多层必填维度、强制行业分类或复杂标签关系。收敛也不必走向严格分类，应保留已帮助用户找到资料的多样性。

### 4.6 已比较的其他思路

| 方法 | 价值 | 当前定位 |
| --- | --- | --- |
| 固定分类或结构化属性 | 含义明确、路径可预测 | 可比较，不能成为初版强制完整体系 |
| 名称查找 | 利用现成线索，减少标注负担 | 已有入口，与标签方向并存 |
| 全文或语义搜索 | 利用正文或含义 | 已有本机正文索引，当前推进片段及相关性检索；真实 Embedding 与混合检索分阶段实施，见 §10.9 |
| 分类文件夹 | 按熟悉的项目、业务直接进入 | 已确认的辅助组织入口 |
| 收藏 | 直达主动选中的资料 | 已确认的个人快捷入口，不代替公共标签贡献 |

### 4.7 全部资料、文件夹与收藏

**已确认：三个入口服务不同意图，基础集合相同。**

| 入口 | 用户意图 | 范围与行为 |
| --- | --- | --- |
| 全部资料 | “我要找一份资料” | 总览本地所有已整理资料，包含各分类中的资料 |
| 文件夹 | “我要处理这一类事情” | 进入稳定的分类集合，再按名称、标签查找 |
| 收藏 | “我要直接使用这份资料” | 进入用户主动保存的快捷引用集合，仍可筛选 |

- 本地分类和本地收藏都以资料属于已整理集合为前提；待整理需先完成整理。
- 同一资料可同时在全部资料、分类位置和收藏中出现，它们不是三个互斥仓库。
- 收藏是主动选择，不等于使用频率排名；偶尔使用但重要的资料也值得收藏。
- 未放入分类文件夹的资料仍是正常的已整理资料，不应暗示必须继续分类。
- 默认进入全部资料，突出名称和标签；分类文件夹在侧栏独立分组，取消“资料库顶层”并列主入口。
- 全部资料和收藏始终可达；隐藏文件夹导航只改变展示，不改变归属。

本节的收藏指本地收藏。共享收藏是远端资料引用，仍按远端权限访问，不代表已经下载，也不混入本地“全部资料”和收藏列表。

**当前工程约束：** 分类对应实际工作路径，一份受管资料只有一个分类存放位置；多维关系由标签表达。收藏不移动文件。尚未决定引入多个虚拟文件夹同时引用同一资料的模型，也不通过复制文件模拟多分类。

### 4.8 收录、整理与后续操作

资料进入待整理区时即建立身份与元数据登记，能确定“是哪份资料、属于哪个区域、工作文件在哪里”。整理时补充标签和可选分类，不能等整理完成才登记。

**已确认的整理规则：** 至少一个有效标签即可完成整理，文件夹可选。不选分类时直接放在库根目录，仍通过全部资料和标签找到。批量整理追加共同标签，保留原有标签；整体文件夹资料保留内部结构。

| 操作 | 改变什么 | 不随之改变什么 |
| --- | --- | --- |
| 完成整理 | 待整理进入已整理集合，可选归类 | 原资料身份和既有历史 |
| 归入 / 更换文件夹 | 分类归属与工作位置 | 已整理状态、身份、标签、版本与收藏 |
| 移出文件夹 | 解除分类归属，当前实现回到库根目录 | 仍属于全部资料，不退回待整理 |
| 加入收藏 | 增加个人快捷引用 | 内容、路径、分类、整理状态与版本 |
| 取消收藏 | 删除快捷引用 | 资料仍在全部资料中 |
| 退回待整理 | 明确改变整理状态，转入待整理区 | 保留身份与历史，不等同于移出分类 |
| 移入回收站 | 暂离正常资料集合，进入可恢复流程 | 不等同于取消收藏，不影响远端共享副本 |
| 永久删除本地资料 | 按本地规则清除登记及可清理内容 | 不能借此删除组织共享资料 |

**当前工程行为：** 资料退回待整理、进入回收站或缺失时，不显示为正常个人收藏；保留尚存引用，恢复为已整理后再次显示。缺失资料通过提示、重新定位或历史版本处理，不把工作文件不可见解释为从未登记。

归类、移出不要求重新打标签、重新建立资料或制造新版本。目标同名内容不覆盖；整体资料内部不能作为分类目录接受其他独立资料。历史索引模式等兼容能力不自动获得移动库外原件的权限。

<a id="foundation-ai-preorganize"></a>

### 4.9 AI 预整理与用户确认（2026-10-20—21）

**问题陈述：** 发起人已经知道大部分资料的内容，主要负担是命名、分类和打标签；现有标签与文件夹体系不成熟，需要在使用中逐步建立。优先通过 AI 准备可直接采用的整理方案，减少填写和决策操作，同时为后续查找积累可靠信息。

**当前确认方向：** 默认流程为「收录并登记 → 待整理中 AI 后台预处理 → 用户查看或调整 → 一次确认完成整理 → 进入文档库」。此前讨论过直接自动入库，随后修正为保留用户介入和最终决策节点；自动执行仅作为后续主动启用的可选方向，不能作为当前默认流程或已实现能力。

AI 提出名称、标签、分类和有依据的关联建议，TeamHub 在用户确认后执行实际整理。建议生成本身不改正式名称、标签关联、工作位置或资料状态；不需要用户打开聊天窗口逐份指挥。支持一次采用整套方案、按需修改及批量确认的交互方向，避免逐字段、逐标签审批。

**独立展示 AI 预整理状态：**

| 状态 | 含义 |
| --- | --- |
| 待 AI 预整理 | 尚未生成整理建议 |
| AI 预整理中 | 正在分析并准备方案 |
| AI 已预整理 · 待确认 | 可查看、可调整的方案已生成，尚未应用 |
| 预整理失败 | 未生成可用方案，显示原因并支持重试或手工整理 |

上述状态均属于待整理中的辅助处理状态，不增加第三个资料仓库。用户确认并成功完成整理后，资料才进入文档库；文件夹是可选分类入口，不选分类仍属于全部资料。沿用 §4.8 至少一个有效标签的规则，本轮没有取消标签要求。预整理状态、内容索引覆盖状态和待整理／已整理状态分别表达，不能互相替代。

**建议原则：** 原名清楚时优先保留；标签优先复用、必要时建议新增；文件夹保持少量、浅层，没有合适分类可以留空。体系通过用户采用与纠正逐渐形成，不预先要求完整词表，不让 AI 批量制造深层目录。人工修改优先，已确认结果仍可调整。

**与索引及伙伴的关系：** 人工标签表达使用习惯，索引表达实际内容及来源，二者共同服务准确查找。快速整理、深入建档是两档资料预处理，均共用尽可能完整的基础索引；差别在 AI 理解和派生线索的丰富程度，不能用抽样、摘要或简卡代替全文底稿。索引可后台继续，不作为用户确认入库的前提，未覆盖部分须明确。专题分析是伙伴围绕具体问题执行的独立对话任务，不是第三级整理。具体设计和实施阶段见 §10.9；资料操作仍由 TeamHub 执行，普通聊天直接发送的现行规则不因此改变。

**资料理解成果长期复用（2026-10-21）：** 预整理中“资料讲了什么”的理解进入 §10.8 的资料卡，“为什么建议这样命名、打标签和分类”留在整理方案。卡片可以在待整理阶段使用，用户不采用整理建议也不应丢弃有效理解成果。确认整理只确认资料管理操作，不等于逐条认证 AI 判断。人工标签与 AI 检索词继续分别维护。

**启用与外发：** 自动预整理默认关闭。用户可一次启动选中批次，也可主动开启当前个人库的待整理及以后新收录资料；范围说明包含目标服务、已保存资料的文字和必要图像、已有标签和分类名称。配置密钥不等于授权全库外发，最终整理确认也不能追溯授权此前的调用。服务配置改变后暂停旧后台授权；关闭自动模式不取消另行明确启动的批次。普通聊天仍直接发送。

**内容与操作：** Hermes 在单份资料的已保存版本范围内阅读并提出结构化方案，不能修改文件或读取其他资料来猜测关联。方案与内容索引独立；真实阅读范围、解析和缩放等缺口由宿主记录，不能仅凭模型自述判断完整性。采用前核验资料版本、管理信息及工作内容；批量逐份事务执行并显示部分失败，重复请求不重复执行。

整体收录的文件夹纳入 AI 预整理范围：AI 阅读整套快照中的必要成员，准备整体名称、标签、分类和汇总资料卡，用户确认后才完成整理。内部文件不拆成新资料、不自动改名或重新归类，内部目录结构保持完整。整体文件夹资料与作为整理目标的分类文件夹仍是两种不同对象；成员理解及覆盖规则见 §10.8.5。

**撤销与恢复：** 撤销本次整理恢复原名称、标签及待整理位置，不改变内容版本，也不同于撤销收录。后续人工修改、标签身份变化、工作内容变化或原位置占用时，不覆盖后续工作。运行中断和付费状态未知的任务不自动重放；AI 不可用时手工整理始终可用。

价值与范围见[产品方案](AI预整理与用户确认产品方案.md)，任务与接口见[实施蓝图](AI预整理实施蓝图.md)，操作见[使用指引](../guides/AI预整理使用指引.md)。本轮实现及最终桌面包已通过隔离工程验收，证据见[预整理验收](../reviews/AI预整理验收-2026-10-21.md)；真实业务收益仍须试用验证。可选自动入库及从纠正中自动学习个人偏好仍属后续方向，不能与本轮自动准备方案混同。

## 5. 贡献动力与操作成本

### 5.1 已识别的行为问题

发起人接受了以下分析：整理成本发生在当下，而“下次更容易找到”的收益发生在未来。用户取到文件后，可能没有动力进一步补充标签。

收藏可以以更低的成本满足一部分个人回找需要，因此不能仅凭“用户下次还会用”就假定用户一定持续贡献公共标签。

### 5.2 激励方向与延期事项

**已确认方向：** 探索恰当的奖赏和认可机制，使维护者获得回报，愿意参与共同整理。

发起人提出过按标签使用率排名。合作伙伴提出的顾虑包括：热门标签不等于高价值、少见但关键的贡献可能被低估、排名可能诱导堆积标签；也提出过让贡献者看到实际帮助的反馈方式。

**未决 / 延期：** 排名、积分、贡献反馈、奖励形式、衡量方法均未定案。讨论这些可能性，不构成采纳某一激励方案的决策。

### 5.3 易用性约束

- 激励不应被默认视为足以抵消额外操作成本。
- 低频的共享决策可以承担必要的边界确认。
- 高频的标签补充应尽量顺手，不要求用户反复判断多种属性和可见性。
- 功能上的灵活性要与实际操作负担一并评估。

这些约束直接影响了双标签机制延期和初版标签跟随文件可见范围的选择。

<a id="foundation-visibility"></a>

## 6. 私有、共享与标签可见范围

### 6.1 默认私有，主动共享

**已确认：** 个人资料默认仅本人可见，共享是主动行为。收录、完成整理、归类或收藏均不等于获得共享许可。

理由来自隐私、敏感资料边界，以及全体使用者对共享质量的需要。大量未经筛选的资料会降低查找价值；主动共享形成选择边界，但不自动保证内容质量。

“仅本人可见”是应用范围的默认行为，不是对操作系统账户、电脑管理员或文件加密能力的额外承诺。

### 6.2 标签范围跟随所属资料副本

初版不要求每次打标签都选择私有或公开属性。共享的是“资料与标签的关联”，不是把同名标签下的所有私人资料一起公开。

| 操作或所在范围 | 标签如何处理 |
| --- | --- |
| 管理私人资料 | 标签留在个人库内 |
| 首次主动发布 | 确认范围与随行标签，标签随该次发布进入共享空间 |
| 在共享资料上补充标签 | 按权限成为同一共享范围内的标注 |
| 编辑本地副本的标签 | 保持本地修改，不因存在共享关联而自动传播 |
| 取回共享资料 | 新本地对象可以有自己的整理信息；不表示远端支持私人标签层 |

共享不表示互联网公开。既有工程以团队、工作空间及成员权限限定可见性；新增产品规则要求进一步支持资料级的指定成员范围，见 §6.4。首批组织如何映射空间仍需核实，不能以同空间成员身份推导出可以访问其中所有资料。

本地与远端具有独立对象及标签关联。现有“云端同步”等字样不能推导出自动上传私人标注或双向镜像。更新共享内容版本也不意味着自动覆盖全部共享标签；明确操作以契约为准。

### 6.3 双标签机制仍然延期

曾讨论在同一共享资料上并存公共标注与仅自己可见的标注。发起人认可其潜在价值，也指出额外判断和操作成本可能抵消维护动力。

初版不引入共享对象上的双标签属性及逐次可见性选择；待真实需要明确后再评估。私人副本有自己的标签，不等于已实现共享对象双标签。

<a id="foundation-targeted-access"></a>

### 6.4 指定成员共享与管理员访问边界

**已确认（2026-10-05）：** 存在只分享给一个人或其中几个人的需要。云端应支持按资料指定接收成员，不要求为每次分享新建一个空间。资料的可见范围与标签分开：标签帮助寻找，不能作为授权依据。

**规划中的两种范围：** 全空间共享由有效空间成员按角色访问；指定成员共享由发布者和被授权成员按所授能力访问。同空间的其他普通成员不能从搜索、详情、标签、历史、数量、查重或活动记录得知受限资料内容与存在。指定范围下的组织资料仍按组织资料持有规则保存，可见人数少不等于退回私人所有。

**用户明确确认：组织管理员在应用内不默认看到定向共享和资料投递的内容，须获得明确授权。** 账号、团队和空间的管理角色不能直接变成受限资料读取权，也不能通过管理页面或旧接口绕过。该规则限定应用内权限，不宣称阻止服务器维护者直接访问数据库或磁盘。

查看下载、补充标签、提交版本、管理授权和再次分发是不同能力。接收者有权看或协作，不自动意味着有权扩大范围、转投或删除组织资料。具体矩阵、初始管理者及离职移交见 Q-15/Q-18；蓝图提出可查看／可协作和资料管理者的候选方案，尚未把全部细则视为逐项确认。

共享授权和投递授权必须分别辨认：共享授权围绕资料对象，投递授权围绕一次发送的确定附件。撤回一次投递不取消其他独立共享或投递资格；仅有附件权限不能读取源资料的其他版本或标签。取消授权只能停止后续云端访问，不能自动收回已经下载、独立保存的个人副本。

<a id="foundation-ownership"></a>

## 7. 文件归属、共享副本与删除权

### 7.1 个人与组织共享的边界

**已确认：** 共享成功后，服务器独立保存内容及元数据，不依靠上传者本地路径提供文件。共享资料作为组织集体资料持续保留。

本节的共享指“发布为组织共享资料”，包括限定成员可见的组织资料。仅通过投递传送、尚未发布的附件是否纳入长期组织资产及保留期限仍待确定（Q-17），不能因共用服务器存储就自动套用相同归属和清理政策。

1. 本地整理、移动、改名、取消收藏、删除或电脑离线，不应使已发布资料消失。
2. 本地编辑不自动修改远端。再次共享明确选择延续原资料或另建资料。
3. 取回在本地形成独立工作副本，同时记录来源及版本关联。
4. 上传者不能仅凭本地操作决定共享资料存续。
5. 成员退出后已共享资料保留，私人资料不因退出而必须上交或保留。

判断一次操作属于哪一端，应看资料所在范围：桌面中的“待整理／文档库”操作个人资料，桌面或网页中的“组织共享库”操作云端资料。使用桌面程序不表示该操作一定只改本地。

“属于组织”表示产品控制与存续方向，不是外部著作权、雇佣关系或法律所有权判断。允许共享哪些资料仍按实际组织要求明确。

### 7.2 删除边界与动作区分

**历史起点：** “只能删除自己上传和产生的内容，无权删除他人的内容”表达贡献保护诉求，但不能直接解释为上传者拥有共享永久销毁权。

**已确认：** 共享永久删除受组织管理员权限控制；重命名、撤回、进入回收站、永久删除应区分，个人删除与共享删除始终隔离。

**当前工程默认：** 共享资料先进入回收站再永久删除，按角色和空间检查权限；账号停用保留资料、历史和贡献。角色、恢复与物理对象清理的具体规则见[数据与接口契约](../architecture/MVP数据与接口契约.md)和[M5 复核记录](../reviews/M5复核与修复记录.md)，不能用“管理员”省略权限范围。

新增指定共享后，组织治理权限与受限内容访问权须分别检查；原空间级管理员判断不能直接沿用为“可以读取、修改或销毁全部指定资料”。定向资料的治理与授权组合、无人可授权时的移交流程由 Q-18 承接。

“组织资料撤回／下架”仍需在使用中明确含义，不能默认等于永久删除大家已使用的资料。“资料投递撤回”则已有独立含义，见 §7.4，两者不能混用。

### 7.3 多人维护的最小约束

**已确认：** 他人可以为共享资料提交新版本，保留版本及提交贡献；自由添加标签不等于任意修改、删除他人贡献。

当前工程按标签关联记录贡献者，普通成员撤销自己的关联，管理员在权限范围内纠错；重复添加不抢占原贡献者。版本提交与并发规则见第 8 节。

以上协作须以拥有该资料相应权限为前提；§6.4 的指定授权不能被空间级 member/admin 身份绕过。

这些安排服务于原则，可按试用证据改善；不能为了简化界面而绕过权限、抹除贡献或破坏组织资料存续。

<a id="foundation-delivery"></a>

### 7.4 资料投递作为独立功能

**已确认（2026-10-05）：** A 在本地生产资料后，可以直接通过 TeamHub 发送给 B 或指定的多个成员；B 被提醒有资料送达，无需先搜索。用户确认“收到提醒即可”，不要求自动保存到接收者本地，并要求该能力作为独立功能存在。

产品提供“收到的资料”和“已发送的资料”入口。发送者选择资料、接收者，可附说明；上传、接收记录与访问处理由系统衔接，不要求先手动发布到全员共享库再重新发送。用户应能区分“供人查找的组织资料”与“发给我的一次投递”，无需了解底层是否复用存储。

**接收规则：** 在线使用时给出未读提醒；离线期间保留服务端记录，下次连接可见。接收者自行查看、下载或“收录到待整理”。未收录前只存在云端接收关系，不构成第三个本地托管区域；网页普通下载也不等同于 TeamHub 本地收录。已发送表示服务端已建立可取用的收件记录，不自动等于接收者已读或文件已经到其电脑。

**撤回已确认：** 发送者可以撤回投递。撤回后接收者仍可看到已撤回的记录，但不能再从该次投递取得附件；不删除发送者本地原件、已发布组织资料或接收者已下载/已收录的个人副本，也不取消其他独立访问权。

**细化方案：** 一次投递绑定确定版本，之后源文件修改不改变已发送内容；不同发送记录各自管理访问资格。整体撤回是首版建议，逐人撤回是否纳入尚未确认（Q-16）。撤回以服务端生效后拒绝新的获取请求为基础，已经开始传输的字节无法追溯收回；具体并发边界见蓝图。仅投递附件的保留、清理和撤回后发件人取用规则见 Q-17，不把“撤回”解释为立即物理删除。

独立投递不自动带来聊天、阅读回执、跨组织转发、协作改稿或系统关闭后的通知承诺。这些能力需要另行界定；本轮开发方案见[云端与资料投递实施蓝图](云端与资料投递实施蓝图.md)。

## 8. 资料身份、版本与哈希

### 8.1 初版目标

**已确认：** 有版本管理，能识别当前确切版本；渐进迭代，暂不深入审批、生效关系和特定设备适用性。

“已整理”表示进入个人正常使用集合，不表示内容审核合格。“当前版本”表示系统记录的当前内容版本，也不能自动解释为获批、生效或适用于所有业务。

### 8.2 哈希负责查重和完整性

个人归档、共享发布发现相同内容时，提示已有资料并提供入口；取回与迁移时校验内容。目的是减少重复与错拿，不是仅凭相同内容自动合并业务资料的身份、标签或历史。

**双向实体查重（2026-10-13 用户要求）：** 从云端取回和向云端推送都需要查重，整体目标是减少两端的文件冗余与版本混乱。以下规则适用于新增资料与投递附件收录，不用来替代已有资料的版本更新：

| 场景 | 判断与处理 |
| --- | --- |
| 取回／收录投递附件 | 对当前个人库中待整理和已整理资料的实际工作内容查重；命中提示“本地已存在”，提供已有入口，不新增工作文件、资料、版本或来源关联 |
| 推送／网页上传新资料 | 在目标云空间中，对本人有权访问、尚未回收资料的当前版本查重；命中提示“云端已存在”，不重复建立资料或首版；“另建”也不绕过相同内容检查 |
| 更新已有资料 | 依据明确的本地—共享关联延续身份；与目标当前版内容相同则沿用，不生成无意义版本；不同内容按既有基准与保护规则提交或接收 |
| 只命中历史内容 | 不能据此声称当前文件已经存在，也不能擅自切换当前版本；历史保护和显式恢复仍有独立价值 |

单个实体文件按完整字节内容的 SHA-256 判断，名称、标签、归类和“普通文件／压缩包”标记不参与同一内容判断。同名但内容不同不是重复。整套文件夹按规范化清单比较相对路径、目录结构与文件内容，不能将单个文件和文件夹混为同一实体。

本地当前工作文件可能已被外部程序编辑，查重不能仅使用数据库中旧快照的哈希；读取期间发生变化或无法可靠读取时应中止并明确提示，不把“无法检查”当成“不重复”。本地范围限当前接管资料，不扫描用户全盘。云端查重必须遵守即时权限，不透露不可见资料的存在，不扩大既有授权。

命中相同内容不自动合并身份、标签、收藏或历史，不自动替换已有来源，不将“文件在云端存在”解释为“这份本地资料已共享成功”。底层不可变对象仍按内容寻址复用；必要历史记录不能作为垃圾版本随意删除。

X 修改一个字后哈希变化，只能说明内容不同，不能证明它是 X 的下一版。相同内容也可能在不同项目中有不同用途。资料延续独立记录，不能由哈希推断。

### 8.3 对象、工作副本和版本分别记录

| 概念 | 用途 | 变化规则 |
| --- | --- | --- |
| 资料身份 | 持续指认“这份资料” | 改名、归类、取消收藏和迁移不创建新身份 |
| 工作副本 | 当前打开、编辑的内容 | 可以修改或移动，不能作为永远不变的历史内容 |
| 版本快照 | 保存某次确定的内容 | 保留旧版，不随工作文件编辑而被覆盖 |
| 哈希 | 查重、比较内容及校验 | 不替代身份或业务版本关系 |
| 本地—共享关联 | 识别共享来源、对象和提交基准 | 不等于自动同步或共同删除 |

本章“未保存修改”指工作内容尚未记录为 TeamHub 的确定版本；即使已经在 Word 等外部程序中保存到磁盘，也仍可能属于这种状态。外部程序保存文件与 TeamHub“保存版本”不是同一个动作。

**当前工程：** 资料采用稳定 ID，标签和本地收藏关联资料对象；区域归属与工作位置分开登记。收录到待整理时即建立身份与初始版本保护，完成整理不是首次登记时刻。

**恢复版本规则（2026-09-30 用户确认）：** 点击恢复某个历史版本后，工作副本直接切换为该版本内容，并将所选历史版本设为当前版本；恢复操作本身不新增内容版本。若工作副本有尚未保存的修改，系统先自动创建保护版本。待整理／已整理状态、名称、分类、标签与收藏保持不变，恢复行为记录到操作日志。用户无需额外导出即可继续使用。其他历史版本保留；历史快照损坏或操作失败时不得以成功提示掩盖失败。

**本地历史版本清理（2026-09-30）：** 用户可主动删除非当前本地历史版本，以减少版本列表数量；当前版本保留，删除不改变工作文件或云端版本。版本编号不重排，后续版本不复用已删除编号。当前工程先删除版本记录，底层不可变快照暂保留，不把版本列表清理等同于磁盘空间回收，也不据此授予成员删除组织版本的权限。

### 8.4 版本延续与“覆盖共享”

**已确认：** 同一资料的连续版本独立保留关联，不能只凭文件名、路径或哈希猜测。再次共享可延续已有资料，也可在内容确有不同且用户明确选择时另建资料；相同内容按 §8.2 提示已有入口。

“覆盖共享”是历史讨论用语，实际表示追加新版本并保留旧版；界面宜用“提交新版本”等明确表达。他人提交也保留作者和版本记录。

**当前工程默认：** 成功提交的新内容成为共享当前版本，相同内容沿用已有当前版；基准过期时报告冲突，不静默覆盖或自动合并。这是简单版本管理，不是审批体系。

此处“相同内容”指与该共享资料的当前版本相同；查重命中其他资料或更早历史，不自动把它们变成共享当前版。两端的编号、接收方式与提交基准分别见 §8.7—8.9。

### 8.5 身份延续与多人积累

标签与历史需围绕可识别资料持续积累。下载、改名、再次加入不能仅凭相似名称自动解释为同一对象，也不应在需要延续时只能创建无关联副本。

既有发布和取回通过关联记录承接来源；复制、重复收录、多来源引用等复杂情况仍需按场景验证。建立 ID 不代表所有身份关系问题均已解决。

### 8.6 整体文件夹资料与压缩包

**已确认：** 一套文件夹可以作为一份资料整体收录、保存版本、发布和更新；初版不提供内部逐文件的独立版本、标签协作或合并。普通文件和压缩包也可以成为资料对象。

这里的文件夹是“整体文件夹资料”，不是“分类文件夹”。前者有资料身份和版本，后者组织多份资料。归类不改变资料内容快照；不能未经明确收录，就把分类目录及其中各份资料合并解释为一个共享对象。

具体快照封装和压缩包预览范围由契约限定，不因此扩大为解包协作或复杂目录同步。

<a id="foundation-cross-end-versions"></a>

### 8.7 两端独立版本与跨端操作

**已留底并实施的方向（2026-10-05，2026-10-13 复核）：** 本地与云端分别持有资料对象、版本历史和当前版本。发布、取回建立可追溯的关联，不把两端变成自动保持一致的镜像。下述更新、来源和基准规则已进入本机工程及隔离验收，详见契约 §10.3；本轮再按 §8.2 完善实体查重。真实组织部署及长期使用效果仍需独立验证。

本地 V5 可以对应云端 V2。版本号只在所属资料对象内表示记录次序，不用于跨端比较新旧；恢复后，当前版本也不一定是编号最大的版本。本地有十个历史版本，首次发布可以只选择其中一个，云端无需接收其余历史。

| 操作 | 本地版本结果 | 云端版本结果 |
| --- | --- | --- |
| 编辑工作文件 | 工作内容改变；由 TeamHub 保存版本时形成确定快照，不覆盖已有快照 | 不变 |
| 恢复本地历史版本 | 工作内容与当前指向切换到所选已有版本；恢复本身不新增，未保存修改另行保护 | 不变 |
| 首次发布到组织 | 保留本地历史，记录所发布版本与共享版本的对应关系 | 建立共享资料及首个共享版本，不复制全部本地历史 |
| 首次取回到 TeamHub | 建立独立本地对象及初始版本，登记具体共享来源 | 不变 |
| 更新已有本地资料 | 接收不同于本地当前快照的云端内容时，新增本地版本并切换工作内容；相同内容见 §8.8 | 不变 |
| 提交共享新版本 | 保留本地资料与历史，记录本次提交结果 | 在对应共享资料上追加版本并设为当前；基准与重复规则见 §8.9 |
| 删除某端资料或本地历史版本 | 只按本地规则处理，不把删除请求传播到云端 | 只按组织权限处理，不连带删除已经取回的个人副本 |

桌面从受管个人资料发起发布和提交时，发送对象必须是一次确定的内容快照。首次发布捕获实际工作内容，不能发送与当前实体不符的过时快照。捕获后先进行云端重复预检；已存在时停止，不为未发生的发布额外新增本地内容版本。确需发送且工作内容尚未保存为版本时，将捕获内容保存为本地版本再发送；上传中继续编辑不能替换已经冻结的本次内容。只发布所选内容及确认随行的元数据，不把自动保护版本或其他私人历史一并上传。网页上传不要求先建立本地 TeamHub 版本，但同样须使接收内容与云端记录一致。预检用于减少重复传输，服务器仍须在正式提交事务中再次检查。

更新内容不改变本地资料 ID、待整理／已整理状态、名称、分类、标签和收藏；本地整理信息与共享整理信息仍各自生效。用户主动另存为新资料时，才走新对象的取回／收录流程，不能以改名、同名或同哈希自行决定对象归属。

网页普通下载只把文件保存到浏览器选定位置，不自动登记进本地 TeamHub，也不建立可直接更新的本地关联；网页直接上传则在云端发布或提交，保留本机原文件。普通下载、网页上传与桌面“取回到 TeamHub”不能混称为同一种本地接管行为，入口边界见 §9.7。

<a id="foundation-local-update"></a>

### 8.8 更新本地：保存接收版本，再切换工作内容

**核心规则：** 用户主动“更新本地”后，系统接收目标共享版本；目标内容不同于操作前本地当前已保存版本时，新增本地版本并将其设为当前，工作文件使用该内容。已有本地历史不被覆盖。恢复是在本地已有历史中选择，更新是接收云端内容，两种动作应明确区分。

例如：本地当前为 V3，工作文件与 V3 一致；接收内容不同的云端 V2 后，新增本地 V4，标明“接收自云端 V2”，并切换工作文件。本地 V1—V3 仍可恢复。如果本地最高分配编号已经是 V8，即使当前恢复到了 V3，新接收版本也应从 V9 开始，不复用旧编号。

若工作文件还有未保存的修改，先自动保存这些修改，再接收云端内容。例如最高编号为 V3，且云端内容与当前快照、工作文件都不同时，修改保护为本地 V4，云端内容保存为本地 V5；V5 成为当前，V4 清楚标注“更新前自动保存的修改”。普通更新由一次明确操作完成，系统不要求用户先手动导出或备份。

**重复内容与边界细化建议：** 为避免不必要的版本，同时保留可解释的接收记录，需要同时比较三个内容：操作前的本地当前快照、实际工作文件、固定的云端目标版本。以下是后续实现建议，不能只检查前两个版本号或一个哈希就跳过流程。

| 内容关系 | 建议结果 |
| --- | --- |
| 云端目标、本地当前快照和工作文件均相同 | 不创建版本、不改工作文件；确认并补充对应关系，提示内容一致 |
| 云端目标等于本地当前快照，但工作文件另有修改 | 不得提示“无需更新”并忽略修改；用户选择采用云端内容时，先保护修改，再将工作内容切回原当前快照，不再新增重复的接收版本 |
| 云端目标等于工作文件，但不同于本地当前快照 | 将这份工作内容保存一次并设为当前，记录云端对应关系；无需再制造一份相同内容的保护版本或重写工作文件 |
| 云端目标不同于本地当前快照，也不同于工作文件 | 工作文件有未保存修改时先保护，再新增接收版本；工作文件未修改时只新增接收版本 |
| 云端目标只与更早的某个本地历史版本相同 | 因本次明确选择的是“接收云端更新”，仍新增接收记录；底层内容可复用。若用户意图是恢复已有历史，则应使用恢复入口，不制造新版本 |
| 同一次更新成功后再次点击或因响应丢失而重试 | 复用已完成结果，不重复接收、不重复保护；期间发生新编辑时重新判断，不能重放旧操作覆盖新修改 |

物理内容去重与版本记录是两个层面：相同内容可共用一个不可变快照，但不能仅凭哈希合并不同资料身份、作者或操作历史。补充云端对应关系也不改写原本地版本的作者、创建时间或形成原因。

**完成与失败边界的设计约束：**

1. 开始时固定目标共享资料及版本 ID，先下载到暂存位置并校验，校验前不替换本地工作内容。云端随后又有新版本时，本次仍准确记录已接收的目标，不能冒称始终是“最新”。
2. 真正切换前再次检查本地工作内容；若下载期间出现编辑，须重新保护、重新判断或明确中止重试，不能用之前的比较结果覆盖新修改。
3. 工作内容、当前版本与来源关联一致落定后才报告成功、更新提交基准。失败时保留或恢复原工作内容及原当前指向，未完成结果可识别、可恢复；若保护版本已经可靠保存，可保留并说明，不伪装成云端更新成功。
4. 首版不自动合并文件或整体文件夹。回收、失权、离线、内容校验失败和本地定位异常应返回明确状态，不能以创建无关联副本冒充更新成功。实现时需验证中断恢复能力，文档规则本身不等于已有断电恢复保证。

### 8.9 版本来源、提交基准与多人修改

**细化建议：** 关联需要分别表达下列三类信息，不能只保留一个含糊的“已同步版本”：

| 信息 | 用途与更新时机 |
| --- | --- |
| 版本来源／对应关系 | 说明哪个本地版本取自或发布成哪个共享版本，关联服务身份、空间、资料与版本 ID；随成功接收／提交记录，不随改名、分类或本地恢复而改写历史 |
| 已确认的共享提交基准 | 通常由最近一次成功接收或提交确认；显式处理冲突时也可确认新的基准，并留下记录。提交时核查该共享版本是否仍为当前，不能由查询自动刷新 |
| 最近观察到的共享当前版本 | 用于“云端有更新”等提示；浏览、搜索、刷新、预览本身不表示已经接收，不自动推进提交基准 |

服务器连接地址与服务身份应区分，换地址不能被当成另一份资料或把凭据误送到别的服务；具体身份与迁移机制仍由 Q-11 承接。此处规定关系含义，不在基石预定数据库字段或要求引入完整分支体系。

**多人协作按以下方向处理：**

- A、B 都基于共享 V1 修改，B 先提交成 V2；A 仍以 V1 为基准提交时，返回冲突，不静默覆盖、不自动改基准后重试。已经成功的同一请求重试返回原结果，不额外增加版本。
- 本地与云端都有变化时，即使本地修改已经保存，也应明确提示两端有不同内容，供用户选择保留本地继续处理，或采用云端并保留本地历史。需要合并时由用户处理，本系统不自动解释文档内容。能够恢复旧版并不等于已把两方修改合并。
- 主动采用云端内容并成功更新后，才推进接收基准。仅把另一方文件下载到磁盘用于比较，不代表已经完成更新或解决冲突。用户手工处理差异后，可通过明确的冲突处理动作确认“以共享 V2 为基准提交这份内容”，记录该选择；服务端仍须核查 V2 是否为当前，不能自动刷新基准来绕过冲突。
- 恢复到旧的本地版本，只改变本地工作内容和当前指向，不改变云端、不倒退已确认的提交基准。再次发布旧内容时，应明确提示“将旧内容作为新的共享当前版本提交”；若基准之后云端又有更新，仍须处理冲突。恢复出来的内容不能自动被解释为包含了后来云端的修改。
- 在有效基准下，拟提交内容与共享当前版相同，可确认已有版本而不新增；内容仅与共享更早历史相同、但不同于共享当前版时，明确提交会形成新的共享版本，保留中间历史。相同哈希不能绕过权限检查或擅自清除未解决的基准冲突。

本地版本删除与云端独立。后续实现应使必要的共享对象关联和已确认基准不依赖某条可删本地历史记录继续存在；原版本删除后，不再宣称可在本地恢复它。组织历史版本的删除权限、保留与清理策略由 Q-14 另行讨论，不直接沿用个人删除规则。

### 8.10 投递内容与版本权限

**本轮工程方向：** 投递保存发送时的确定内容及独立引用，不指向会变化的工作文件或“届时的云端当前版本”。源资料更新、个人删除或源入口回收不能静默改变附件；物理内容清理须检查共享版本与投递附件等全部引用。

收到某个版本的投递，不等于被授予源资料的全部历史、后续版本或提交权。主动收录附件时记录投递来源并建立本地初版；不能自动生成可向源资料提交的共享关联。若已有独立共享授权，用户可以从共享入口另行取回或更新，仍按 §8.7—8.9 管理。

底层可复用相同的不可变内容，权限、来源和投递记录仍分别成立。转投、源资料永久删除及存储回收的实施约束进入蓝图，相关未决留存政策先明确再对真实资料启用。

## 9. 存储区域、服务连接与部署

### 9.1 业务集合、物理位置与访问范围

| 边界 | 要回答的问题 |
| --- | --- |
| 业务集合 | 是否已整理、属于哪个分类、是否收藏、是否主动发布 |
| 物理存放 | 工作文件、数据库、历史版本保存在哪里 |
| 访问与运行 | 谁可以访问、由哪个服务处理、服务部署在哪里 |

共享、备份与迁移也不同：共享使他人按权限获取资料，备份支持故障恢复，迁移改变存放位置。不能用其中一项自动证明另一项成立。

### 9.2 收录方式与个人资料边界

**已确认：** 桌面拖拽进入待整理采用移动源文件，目的在于集中整理。成功收录后不在原位置额外保留工作副本；用于保护历史的系统快照有独立用途，不等于散落复制文件。

移动需明确结果并保护完整性，失败时保留或恢复来源并提示实际状态。历史复制、索引兼容功能不改变这一主要交互约定，也不授权迁移程序处理所有库外文件。

个人电脑可以保留“已发布资料的本地副本”或“取回副本”，但组织共享正式内容由服务器独立保存。“个人电脑不存在共享文件”应理解为个人文件不是直接供组织访问的共享源，不能字面解释为本地不得存在副本。

### 9.3 两个存储区域独立配置

**已确认：** 文件库和待整理区可以独立，也可以任一方包含另一方，但不能完全同路径，也不能将区域根嵌入整体文件夹资料或系统元数据目录。

- 物理包含关系不决定资料归属，归属由登记的区域与位置决定。
- 调整一个区域只移动该区域的登记对象，另一区域保持原绝对位置。
- 例如文件库原为 A、待整理为 A/待整理；文件库迁到 B 后，待整理仍为 A/待整理，需要移动时另行调整。
- 迁移预览必须说明上述范围，不能让用户按“父目录移动会带走所有内容”的直觉猜测。

### 9.4 按登记对象迁移

**已确认：迁移按系统登记的资料归属执行，不把所选目录中的全部内容搬走。**

登记从收录开始，包含稳定身份、区域和位置。迁移据此生成清单，逐项定位、搬运并校验；不是重新猜测文件名，也不是将扫描到的全部磁盘内容视为受管资料。

- 普通资料按对象移动，整体文件夹资料连同内部结构整体移动。
- 文件库迁移携带数据库、标签关系、版本对象和回收站等系统数据；待整理迁移移动其工作资料。
- 已登记对象之外的无关文件、另一区域资料及库外索引原件不因目录相邻而纳入范围。整体资料内部内容属于该对象的范围，无需逐文件另建登记才能整体迁移。
- 保留 ID、标签、版本、收藏及共享关联，仅更新物理位置。
- 先复制与校验，再切换配置，最后清理旧副本；保留持久日志处理中断。
- 缺失、冲突或内容变化应明确提示，不覆盖同名内容，不将部分完成报告为完整成功。

**当前工程限制：** 切换前中断可取消任务并保留目标已复制内容；切换后继续校验清理。旧位置可能保留跳转日志和待核对副本。迁移锁约束本实例，不承诺阻止外部程序修改文件。详见[存储路径与迁移](../guides/存储路径与迁移.md)。

**备份限制：** 现有维护工具以文件库根为备份范围，库外待整理需另行备份，不能将一次个人库备份视为已覆盖两个独立区域。完整备份恢复两个区域的方案列为后续工程事项。

### 9.5 本地服务与组织共享服务解耦

**已确认的产品边界、已有工程实现：** 两端具有独立数据库、文件存储和进程，通过 HTTP API 处理认证、发布、版本提交、共享标签维护和取回；不共用数据库，不直接导入对方业务代码。

普通客户端主要请求链为：

个人桌面 / 用户界面 → 本地服务与共享适配层 → 共享 API → 组织共享服务。

本地适配层维护服务地址、登录会话、资料来源和发布取回；共享服务独立鉴权并保存组织内容。双方仍需兼容 API 格式和语义，“解耦”不等于协议可以任意变动。

可以借 Git 与 GitHub 理解“本地独立工作、明确提交到远端”的边界；TeamHub 不是 Git 实现，不承诺分支、合并或完整历史同步。

**2026-10-05 进一步明确的方向：** 两端独立运行、保存和升级，通信仍依赖兼容的接口契约。本地功能不以云端登录、在线或启动成功为前提；已有数据隔离和 API 通路不能替代这些边界的完整验收。当前一键本机测试入口先启动共享服务属于联调安排，后续本地独立入口不应继承这一运行前提。

用户操作应分别表达“发布到组织”“取回到 TeamHub”“提交新版本”“更新本地”和“维护共享标签”，减少笼统的“同步”字样；所选版本、作用范围和操作结果应可辨识。版本协作规则见 §8.7—8.9；稳定服务身份、接口兼容机制仍需后续工程规划。

### 9.6 云端不绑定公有云

“云端”是相对个人端的服务角色，可运行于本机模拟或组织内网。发起人指出存在敏感信息，因此共享不以公有云为必要条件。

| 方式 | 当前判断 |
| --- | --- |
| 公有云集中保存 | 不是必要前提，不因旧目录名或历史依赖默认采用 |
| 内网集中保存 | 当前后续方向，减少对个人设备在线的依赖 |
| 目录集中、内容散在个人电脑 | 持有人离线仍会影响获取，未选为初版共享路径 |

通用内部服务器便于承载标签、检索、账号和版本应用，故合作伙伴在与 NAS 二选一时倾向服务器；以维护能力为前提，不是采购决定。NAS 偏存储，也可能承载应用；无需现在支持全部部署组合。

内网位置不自动满足组织全部要求。文件名、标签、项目名等元数据也可能敏感，实际允许存放、传输和接入的范围仍需明确。

### 9.7 普通用户连接与管理员部署

服务器部署好且网络可达后，普通用户在客户端保存共享服务地址，登录账号，选择有权限的共享空间即可使用；无需修改源码、重新打包或配置数据库。localhost 指使用者自己的电脑，接入服务器时需替换。

**2026-10-14 已确认并授权实施：** 普通用户使用“共享资料库”的语言，不承担“绑定工作空间”的配置动作。设置中的“云服务”只负责服务地址和账号；云仓库与资料投递顶部显示“组织 / 资料库”，直接选择即可进入。一个账号可以加入多个组织并访问其资料库，列表按实际权限汇集；当前客户端仍一次连接一个云服务，不等同于同时连接多个服务器。

- 只有一个可访问资料库时自动进入；有多个时恢复该服务和账号上次成功选择且仍有权访问的库。没有有效记录时展示资料库入口，由用户点击选择，不默认进入列表第一项。
- 暂无资料库时说明需联系管理员；加载失败提供重试，不把网络故障解释为无权限，也不强迫普通成员创建组织。
- 当前选择影响浏览、投递上下文及新发布的建议目标，不搬动本地资料，不自动共享，也不改写已有云端关联。
- 从本地发布新资料时直接选择“发布到”的资料库并核对范围；对话框选择不改变云仓库的浏览位置。已经共享的资料选择“更新原资料”，须显示并固定原组织、资料库和云端资料，不能因浏览切到其他库而更新错误目标。
- 管理页面负责组织、资料库和成员，其管理选择与普通浏览选择独立。重试沿用已确认的目标与内容；账号、服务、个人库变化及失效权限不得让迟到响应跨上下文生效。

操作路径见[共享资料库使用指引](../guides/共享资料库使用指引.md)。选择资料库只是访问入口，不改变 §6 的授权、§7 的归属或 §8 的版本和查重规则。

这是以服务、网络、账号准备完成为前提的客户端使用路径。现有共享库换址或迁移还涉及旧会话、收藏和发布关联中的服务标识，不等同于首次接入，需专门验证，见 Q-11。

**管理后台工程现状：** 已有独立 Web 页面与管理员 API，提供统计、用户启停与管理员身份、团队管理等基础能力。管理页面直接通过 API 访问共享服务，与普通桌面的本地适配链不同。

部署云端 API 不会自动部署后台页面。页面托管、目标服务地址、安全策略和实际管理操作仍需内网验收。已有 admin.html 不等于完整后台上线。

**新增产品共识（2026-10-05，待实施验收）：** 普通成员无需安装 TeamHub，即可通过浏览器登录、查找和下载有权限的组织资料，也允许通过网页上传新资料或为已有资料提交新版本。桌面共享入口与网页使用同一套共享服务及权限规则；普通成员网页与组织管理后台的职责分开，不因能上传而获得管理员权限。

网页“发布到组织”应明确其共享行为，上传保留本机原文件，不接管其位置或自动建立本地 TeamHub 关联；普通下载同样不等于“取回到 TeamHub”。网页提交已有资料的新版本仍须选择目标资料、遵守基准和贡献记录规则，不能因入口不同而绕过 §8 的版本约束。

### 9.8 本机验证与真实部署

当前可以在一台电脑上模拟个人与共享服务，仍须保证数据独立。部署到独立服务器时服务契约保持一致，但目标系统、依赖安装、网络、权限、运行维护和恢复均需核验。

已有 macOS ARM64 本机与桌面包验证记录，不等于其他服务器平台、全新机器安装或约 10 人真实使用已通过验证。

## 10. 技术选型与 MVP 范围

### 10.1 当前技术构成与理由

| 层次 | 当前采用 | 与目的的关系 |
| --- | --- | --- |
| 桌面外壳 | Electron | 本地文件拖拽、打开、窗口与后端启动 |
| 用户界面 | Vue 3、Element Plus、Pinia | 整理、标签、分类、收藏及共享交互 |
| 本地服务 | FastAPI / Python、SQLite | 个人身份、工作文件、快照与配置 |
| 本机智能体引擎 | 随应用交付的独立 Hermes 工作进程 | 按任务调用模型与 TeamHub 资料工具，保持资料规则与智能体引擎可独立维护 |
| 共享服务 | 独立 FastAPI，当前开发使用 SQLite | 账号、空间、权限、共享资料与版本 |
| 内容保存与传输 | 受管文件对象及快照，通过 API 上传下载 | 独立保存、完整性校验与历史保护 |

这套架构服务于本地文件能力和小规模内网验证，尚无证据要求微服务化或全面重写。共享端其他数据库配置能力不等于完成对应部署验收。

旧 OSS 预签名路径、设备 manifest 共享和通用双向同步不是当前主通路，历史存在不能定义新需求。cloud_backend 是目录名，不表示公有云依赖。

### 10.2 从旧代码到当前实现

早期选择保留主要栈、可用界面与模型概念，重建版本保护、发布取回、共享权限与删除等关键流程。此后已进入 M0—M6 的实施、复核和修复，并持续完善桌面与整理体验。

因此“测试只覆盖 pointer”“版本路由未接通”等应作为历史问题阅读。是否处理及验证方式查复核记录，不能把旧缺陷冒充当前结论，也不能以本机通过证明所有条件下可靠。

v0.4 修订时引用的个人后端相关回归记录为 170 项通过，并有临时库桌面操作验收；后续结果以带日期的[验证记录](../reviews/MVP验证记录.md)及专题记录为准。本版未因文档修订重新运行测试，这一历史数量不是当前全量测试数、共享端全部测试数或产品效果评分。

### 10.3 当前 MVP 核心闭环

1. 文件、压缩包和整体文件夹资料纳入个人管理，登记身份与位置，默认私有。
2. 拖拽进入待整理，补充标签完成整理，分类可选。
3. 从全部资料、分类或收藏进入，以名称、标签及已建立的本机正文索引发现和使用资料。
4. 已整理后归入、换类、移出或取消收藏，保持对象及历史连续。
5. 独立配置存储区域，按登记清单迁移并保留元数据与关联。
6. 主动发布及取回，他人按权限补充共享标签、提交有记录的版本。
7. 收录与发布检查重复，内容传输校验，版本追加保留旧版。
8. 个人与共享副本隔离，成员退出保留组织成果，删除和贡献撤销有权限边界。

工程证据、限制与未完成事项由契约、指南和复核记录维护。管理后台内网部署完备性属于下一阶段验证，不能隐含计入“本机 MVP 已形成”。

2026-10-05 留底的“接收云端更新形成本地版本”、完整来源与基准规则、普通成员独立网页入口、资料级指定授权及独立投递，属于后续云端规划与实施范围。[云端与资料投递实施蓝图](云端与资料投递实施蓝图.md)以 C0—C7 拆解契约、权限迁移、网页、投递、桌面联动和验收，不表示这些阶段已完成，也不覆盖原 M0—M7 的历史结论。

### 10.5 AI 辅助整理第一期（2026-10-15，既有能力）

2026-10-20—21 的后台预整理与用户确认见 [§4.9](#foundation-ai-preorganize)及[使用指引](../guides/AI预整理使用指引.md)。以下保留既有单份标签建议入口的规则；其逐份摘录确认不替代新预整理的批次或当前库范围启用。

**已确认并授权第一期开发：** MVP 先调用外部 AI API 验证价值，首个服务为 DeepSeek。第一期处理个人端主动选中的单份资料，提供标签建议和简短摘要；自然语言搜索、版本变化说明及跨资料问答按后续价值与实施成本分别评估。

本期服务于减少初次整理成本和帮助用户辨认资料。接通模型、生成更多标签不自动构成成功，仍需观察建议采纳、修改负担和整理耗时。自由标签、个人默认私有、个人与组织副本独立、版本由系统维护的原则持续适用。

- 配置密钥只建立调用能力，不等于授权读取或外发全部资料。
- 用户先查看本机提取的确切摘录、资料名称及目标服务，再明确同意外发。已配置外部 API 的情况下，允许处理的资料范围仍由用户按任务选择。
- AI 仅提供建议；所选标签填入现有表单，保留已有标签，经原保存动作确认。摘要先供阅读，不自动覆盖用户描述或工作文件，不生成内容版本。
- 分析绑定当前工作内容与个人库。更换资料、内容、个人库或目标服务后，旧请求与结果不能混用。
- 密钥是本机设备凭据，不属于资料对象，不随资料库迁移、备份或组织共享传播。第一期采用独立配置及受保护的密钥存储，避免把具体服务写死到文件管理业务中。

该阶段不默认进行全库 AI 扫描、标签治理、自动归类或组织资料问答。后续索引继承资料的访问和生命周期边界，本地私有资料不会因启用 AI 而默认进入组织或公网服务。本机后台索引的后续范围见 §10.6。

格式、配置和操作步骤见[AI 辅助整理使用指引](../guides/AI辅助整理使用指引.md)，工程协议与证据分别维护在契约 §10.7 和专题验收记录。

### 10.6 通用资料伙伴与索引基础（2026-10-15—16）

**已确认方向：** AI 应帮助用户发现资料、共同阅读和分析资料、比较内容并形成有依据的回答。电力图纸是重要场景之一，不能据此把系统限定为图纸工具、一次或二次专业助手。标签建议只是入口；通用资料使用能力才是后续方向。

**该阶段授权：** 发起人认可索引 Skill 初稿并授权进入代码阶段，先建立「资料收录 → 本机后台解析 → 可定位的内容索引 → 查找 → 用户确认后的 AI 线索补充」闭环。该阶段成果作为智能伙伴的资料基础；后续自主工具调用、多模态阅读与跨资料分析的新增授权见 §10.7。

1. **收录先建立可靠底稿，提问后再深入理解。** 收录时记录身份、固定版本、原文结构、位置和处理缺口；整理时使用人工标签与分类提供语境。具体故障判断、复杂图纸关系推导和跨资料综合应围绕实际问题开展，避免为所有资料预先猜测全部用途。
2. **成果应可检查、可重建。** 目标索引包括资料概览、原文内容单元、辅助检索线索、来源位置与可验证关系、处理覆盖和缺口。提取原文、人工信息与 AI 推断分开保存；无证据的关联不能写成事实。首版实现原文、位置、覆盖及辅助线索，不把未识别的图像或复杂关系伪装成完整理解。
3. **Skill 规定方法，程序保障规则。** Skill 描述输入、输出、禁止行为和质量标准；解析、任务调度、版本绑定、权限、限额和输出校验由代码落实。规则文本本身不能代替解析器、搜索引擎或权限系统。
4. **索引属于资料的派生数据。** 索引绑定文档 ID、已保存版本及内容哈希，可重建；更新或恢复版本后，旧索引不能继续冒充当前内容。未保存工作修改不属于该版本索引。索引不会创建内容版本，也不改写原文件、人工标签和描述。
5. **整理不等待 AI。** 本机解析后台进行，失败不阻断整理；界面区分等待、进行中、已建立、部分可搜索和失败，并允许重试。已有受管资料逐步补建本机索引，不扫描库外无关文件。
6. **本机处理与外部调用分开授权。** 只在本机建立索引不需要 API 密钥。外部 AI 补充前展示本次确切名称、摘录、元数据和位置标记及目标服务，用户确认后发送。部分摘录必须显示覆盖范围；配置密钥不授予全库自动外发权。

**索引第一步交付时的工程现状：** 首版解析文本、文字型 PDF、DOCX、XLSX，使用本机正文检索和经确认的 AI 辅助词；扫描件、图片、图表、整体文件夹和超限内容明确报告缺口。该索引模块承担检索底稿职责；自主工具调用和问题驱动的多模态阅读由 §10.7 的伙伴模块承接。向量语义检索和组织库索引尚未接入，后续必须按实际访问权限筛选资料及其索引。

**价值验证：** 用真实常见问题与已知相关资料检验能否找回、误命中多少、来源能否核对；分别评估解析覆盖、检索召回和回答依据。索引质量影响查找效果，但提问表达、检索策略、版本范围与权限同样影响结果，不能将正确回答完全归因于收录阶段。

使用见[资料内容索引指引](../guides/资料内容索引使用指引.md)，工程契约见 §10.8，验证见[索引第一步验收](../reviews/资料索引第一步验收-2026-10-15.md)。

### 10.7 AI 智能伙伴与本机智能体引擎（2026-10-16 确认，2026-10-20 更新）

**已确认并授权开发：** 发起人要求将讨论形成的首选路线写入基石并落实代码，明确需要通用 AI 智能伙伴。伙伴能够承接自由问题，持续交流，主动发现和阅读相关资料，比较、分析内容，生成有依据的成果，并在授权范围内执行资料操作。电力图纸只是使用场景之一，标签建议只是既有的单项能力，不作为伙伴的完成标准。

**当前选型：** 2026-10-18 发起人授权集成 Hermes，采用「TeamHub 资料与任务服务 + 独立本机 Hermes 引擎 + 可替换模型 API」。Hermes 随应用交付，由 TeamHub 按需管理工作进程，用户无需单独安装、启动或配置 Hermes；原有 AI 服务地址、模型及密钥配置继续使用。Hermes 与 TeamHub 通过受控接口交换任务、进度、工具请求和结果，资料服务继续掌握版本、授权与实际保存。

**选型演进：** 首版及 2026-10-17 的体验优化采用 PydanticAI，实现了可运行的模型—工具循环。真实试用表明工程流程通过与任务成果好用之间仍有差距，因此引入成熟引擎验证持续工作能力；这不意味着更换框架已经证明回答质量提高。OpenClaw 仍是可比较方案，当前交付路线选择 Hermes，避免同时引入多套助手运行系统。

**伙伴定位：** 资料库是工作环境，文件是处理对象，用户任务是目标。以「围绕资料库工作的 AI 伙伴」为主定位，同时把选定资料后的深入阅读与分析做扎实，再提升自主发现相关资料与完成综合任务的能力。查找、阅读、分析和形成成果属于连续工作过程；不能以增加标签、搜索按钮或安装一个引擎替代实际任务质量。

1. **伙伴通过工具自主工作。** 模型可根据问题选择搜索、改写查询、读取正文、查看原始页面、比较证据、追问和生成草稿的顺序。常见问题可直接回答，不强制用户先选择文件；涉及资料结论时应先取得相应证据。不得把自由对话包装成固定的标签或摘要流水线。
2. **TeamHub 持有资料管理权。** 文档身份、固定版本、权限、标签和实际变更仍由 TeamHub 服务负责。工具接收文档 ID、版本和明确参数，不接受任意数据库语句或任意本机路径。模型不能直接改写 SQLite、历史快照或绕过保存机制处理受管对象。
3. **阅读以问题为中心，兼顾原文与原貌。** 本机索引用于发现和快速定位；需要深入理解时读取所选固定版本的正文、表格或原始页面。PDF 指定页面可以渲染图像，即使页面已有较多文字也不能据此忽略图形。图片、扫描件和图纸交给支持相应输入的模型；模型不支持或格式无法读取时，应明确缺口。不能将改扩展名视为格式转换，也不能声称有限页面等于全篇理解。
4. **授权以本次任务为边界，交互以直接发送为常态。** 默认仅处理用户选中的资料；未选资料时可做通用对话。用户可主动选择在个人资料库中查找和按需读取。页面持续展示目标服务和资料范围，点击“发送”即提交本次问题及相应上下文，不另设每轮准备、勾选和确认弹窗。范围在任务开始时固定，新收录对象不自动加入；服务在页面外改变时须先刷新展示再发送，不能暗中更换外发目标。配置密钥本身不等于授权全库。§10.5 和 §10.6 的摘录预览继续适用于原有单次工具；文件改写、删除、成果保存和共享仍有明确的操作入口。
5. **历史可理解，证据可核对。** 保存会话、问题、回答、工作步骤、资料版本、来源位置、读取范围和生成成果。历史回答说明当时使用的版本；新一轮不得把已变化、已移除或未重新授权的来源当作当前事实。输入资料中的指令按不可信内容处理，不能据此扩大权限。索引、模型推断、原文与用户信息继续区分。
6. **生成成果可以进入资料管理。** 首轮支持生成可预览的文本或 Markdown 草稿，经用户明确确认后作为新资料进入待整理，建立正常文档身份和版本。保存需防重复，不静默覆盖已有内容；生成草稿本身不修改源资料。后续扩展 Word、Excel、原件修改或共享发布时，沿用相同的受控服务与确认原则。
7. **长任务不拖住资料库。** 提供步骤状态、取消和安全错误；会话与任务持久保存，程序中断后明确显示任务未完成，不自动重发可能收费的请求。模型调用期间不长期占用资料数据库会话；提交前校验当前个人库、版本和授权条件，旧结果不能误写到新库。
8. **能力可替换，价值需实证。** 模型、解析器、检索工具与智能体编排保持边界，权限和版本规则不写死到某个供应商中。先用真实问题评价任务完成、资料找回、来源准确、遗漏和费用，再决定扩展方向。未经真实样本验证，不宣称已具备完整专业诊断能力或能可靠理解所有格式。
9. **执行预算服务于任务完成。** 日常使用不要求理解调用次数或执行分段；高级选项可调总预算。内部执行段在同一任务总额内自动衔接，消耗、时间及证据累计，不能反复重置上限。空搜索、单份资料不能读取和引用编号不完整先作为可恢复问题处理，让伙伴换方法或说明已有结论的边界，不清空整轮回答。达到任务总额或反复无进展时保留已得成果、来源及原因，允许一次点击继续或直接发新问题；未知付费状态的失败请求不自动重放。续做沿用固定范围，失效版本和权限须重新核验。图像未保留时说明需按需重读，实际用量与未知计量如实展示。
10. **格式能力按内容和读取方式表达。** 正文、表格、内嵌图片与整页原貌分别处理，不以支持一个扩展名宣称理解其中全部内容。Office 正文为空时，先检查实际引用的内嵌图片；未读到内容要说明原因，不生成虚假来源。图像按问题需要读取，沿用同一服务及任务授权，不因收录或建立本机索引自动外发。Office 内嵌图保留结构锚点，但不等同整页版式、图表或矢量组合。模型的实际图像能力可由用户主动测试，复杂专业判断仍需实际样本验证。

**首轮落实范围：** 个人端独立「AI 伙伴」入口、多会话持续交流、自主关键词及正文检索、固定版本阅读、PDF 原页及图片输入、跨资料分析、来源展示、草稿生成与确认保存，以及任务取消和重复请求保护。组织资料直接检索、向量语义检索、任意原件编辑、自动发布和不受限的本机命令执行不属于本轮交付；未来接入组织资料必须继续按实际登录者的逐资料访问权筛选，不能利用管理员或代理权限穿透私有边界。

### 10.8 AI 资料卡与 Skill 工作方法（2026-10-21）

**已确认并授权实施：** 将一次资料整理中的理解成果长期保存，帮助用户快速了解资料、通过业务语言查找资料，并帮助 AI 伙伴选择阅读对象和原文位置。资料卡是附着于资料已保存版本的结构化派生理解，不是第三个资料仓库，不改写原文件，也不代替原文证据。

#### 10.8.1 通用骨架与内容扩展

| 组成 | 内容及目的 |
| --- | --- |
| 内容概览 | 一句话或简短摘要、资料类型、主要主题，帮助判断相关性 |
| 内容导航 | 章节、页面、工作表、表格、图示分别涉及什么，附真实位置 |
| 关键对象与事实 | 原文支持的设备、项目、组织、时间、编号、参数及关系；关键事实关联出处 |
| 检索与使用线索 | 同义表达、常见称呼、可能适用场景及问题；推测用途与原文事实分开 |
| 依据与理解范围 | 来源位置、实际阅读范围、未读或未识别内容、不确定事项；未知覆盖不能标成全面完成 |
| 人工补充与修正 | 用户提供的背景、用途和纠错，独立保存并标明来源，不被 AI 重生成覆盖 |

采用通用骨架加按需扩展：表格关注工作表用途、字段、单位和数据范围；纪要关注议题、决定和行动；图纸关注图号、设备及连接等实际可辨信息。没有依据的字段可以为空，不把所有资料硬套成电力图纸，不为了填满字段补造内容。名称、标签、分类等既有管理信息直接关联原记录；AI 检索线索不自动变成人工标签。

#### 10.8.2 生成、保存与更新

TeamHub 提供固定快照、结构与原文定位，Hermes 安排阅读，模型形成理解；TeamHub 校验版本、来源身份、结构和实际覆盖后保存。程序能验证来源存在，不能仅据此保证每个语义结论正确。

快速整理取得支持整理建议和初步卡片的依据；深入建档完善章节、工作表、成员及页内线索。两档共用尽可能完整的基础索引，只对 AI 理解深度和派生成果作分档。专题分析是另行发起的对话任务，围绕具体问题核对、计算和综合，复用预处理成果。不能为了等待全部理解阻塞入库，也不能把快速阅读包装成全文分析。对于已整理资料，用户可直接生成或补全卡片，无需退回待整理。两档切换、精确续读等界面与运行能力须按 §10.9 的阶段验收，不能由产品定义推定已实现。

卡片保存于所属资料库的本机数据库，绑定文档 ID、源版本及内容哈希，记录解析、规则与结构版本、生成模型、时间、实际来源、覆盖及卡片修订号。卡片修订与文件版本分离；同一文件版本重生成卡片不制造文件版本。人工补充独立保存，采用并发版本校验，冲突时保留编辑内容供核对。资料库迁移和备份包含这些记录。

| 变化 | 更新原则 |
| --- | --- |
| 保存内容不同的新版本 | 旧卡保留对应关系并退出当前版本检索；启用该资料自动更新时后台生成，否则显示待更新 |
| 改名、改标签、分类或收藏 | 更新管理信息与入口，保留正文理解；不因元数据变化重做模型分析 |
| 恢复历史版本 | 优先复用该版本仍有效的卡片与搜索投影 |
| 人工修正 | 不被 AI 覆盖；涉及旧版事实的补充在新版标为待核对，不静默作为新版事实 |
| 模型或 Skill 更新 | 保存生成依据，按需更新；单纯换模型不自动触发全库付费重算 |
| 失败或取消 | 保留已有有效卡片，显示原因；不自动重放结果未知的付费请求 |

后台更新按逐资料主动开启的范围执行，显示目标服务和后续保存版本的处理范围；更换服务或密钥配置后暂停旧授权。预整理的既有授权可以支持同一资料、同次阅读生成卡片，不自动扩大为所有已整理资料持续外发。卡片继承资料权限与生命周期，历史卡不冒充当前内容，不通过摘要暴露已删除或无权访问的资料。

#### 10.8.3 使用与检索

用户默认看到简明概览、理解状态和来源版本，按需展开导航、事实、检索线索、用途及缺口。名称、标签、正文与资料卡线索共同检索并按资料去重；保留原文搜索以找回摘要可能遗漏的细节。伙伴可先检索候选、读卡定位，再读原文回答；卡片及人工补充明确标为派生理解或用户信息，不伪造本轮原文引用。

#### 10.8.4 Skill 框架与质量

Skill 提供可执行的工作方法，影响模型如何发挥已有能力，但无法替代完整输入、可靠工具、适当上下文和运行机制。采用三层组织：简短共同约定、按任务选择的 Skill、按需读取的专项方法。专项方法按实际内容结构选择，可组合文字、表格和视觉方法，扩展名只作线索。普通聊天不被强制先生成资料卡。

任务 Skill 应明确目标与完成标准、已知输入与工具、阅读方法选择、何时补读或查证、结构化成果与依据、停止及缺口处理，并提供少量能改变决策的典型例子。避免通用口号、重复的权限条文、解析器实现细节和全量加载所有参考材料。权限、版本、真实覆盖、输出结构、保存冲突由程序保障；内容理解、相关性与证据充分性由模型判断。

按需方法必须由宿主提供真实可调用的白名单读取入口；仅在 Skill 中写参考文件链接不代表引擎可以访问。随包发布的方法文本不能扩大资料授权，不开放任意文件、外网或用户文档中的指令。方法版本参与卡片的生成记录与维护。

以固定模型、资料、工具和预算比较旧方法与新方法；观察关键内容覆盖、事实和引用正确性、前几项找回率、人工修正量、重复读取、耗时及费用。普通、混合、缺失、冲突和无答案样本均应覆盖，并保留未参与调优的样本。模拟模型与结构测试只能证明工程契约，不证明真实模型理解能力提高。详细实现与范围见[资料卡与 Skill 蓝图](AI资料卡与Skill实施蓝图.md)，使用见[资料卡指引](../guides/AI资料卡使用指引.md)。

#### 10.8.5 整体文件夹的理解与整理

整体文件夹继续以一个资料对象、一个整体内容版本管理。AI 从该版本的固定快照查看成员清单、按需阅读成员，生成父资料的汇总卡片：说明这套资料涉及什么、各部分起什么作用、值得从哪里查找，并保留有实际内容依据的关联。每条来源同时定位父版本、成员相对路径及成员内位置，避免不同文件的同名章节或相同页码混淆。

新增文件夹理解 Skill，负责观察结构、安排阅读顺序、组合现有单文件阅读方法及汇总成果。文件名、目录层级只是线索，不能据此断定项目、设备、版本或业务关系。程序记录总成员、已读成员与实际覆盖；只列出清单不等于已读正文，未读、不可识别、超限和不确定内容保留为缺口。

文件夹预整理仍由用户一次确认后进入文档库，只采用整套资料的名称、标签和分类。生成方案不改变任何成员；确认整理也不拆分成员、重排内部目录或创建成员级资料对象。个人卡片按原有规则保存、检索和维护，整套内容保存新版本后使旧理解退出当前版本；已启用的逐资料自动更新继续适用，恢复历史版本可复用对应有效卡片。

本轮成员读取用于预整理及资料卡生成，未同时扩大普通伙伴对话的原文工具范围。成员理解先汇入父卡片，不独立持久化。按成员内容哈希复用理解、仅重读变化成员是后续优化方向，当前重新生成仍可能重读。授权和工程验收分别记录，不能以汇总卡片生成成功证明全部成员已充分理解。

#### 10.8.6 多模态与对象专项 Skill

AI 整理覆盖文字、Word、表格、演示文稿、PDF、图片、文件夹和压缩包八类对象。公共 Skill 维护资料身份、事实、来源、卡片和结束条件；每类对象有独立的阅读与整理 Skill。系统按已保存版本的真实管理身份与不可变文件名路由，自动加载当前对象的规则，集合内成员按需加载相应规则；分类结果不等于已经成功解码或模型具备相应能力。

图片整理基于实际原图，照片、扫描件、截图、图纸、图表分别关注主体、文字、位号、图例、连线或坐标轴。没有文字层不能直接判定资料无法整理。图像解码、原图发送、视觉模型、证据和使用者确认共同构成能力，Skill 本身不能代替其中任一部分；模糊、缩放、未读帧及没有依据的专业结论须保留缺口。

压缩包作为普通单文件资料管理，内部成员来源绑定该包的保存版本和相对路径。AI 读取成员形成整个包的汇总卡片和整体命名、标签、分类建议，确认节点沿用现有流程。保持原压缩实体及完整后缀，不拆包为独立资料或重写成员。程序在受控子进程中校验并按需解码成员，异常、加密、嵌套未展开和超限内容明确说明；当前包的成功理解不能证明所有内部文件已经理解。

每类 Skill 的格式校验、独立行为推演、程序测试和真实模型质量评测分别记录。发布时随软件打包，规则升级使旧卡显示待更新，但不自动发起全库付费分析，也不覆盖原卡与人工补充。支持范围以当轮验证的工具和平台为准；不为尚无解析能力的对象只写空泛 Skill 就宣称已经支持。

### 10.9 AI 整理与准确检索（2026-10-22 建立，2026-10-23 更新）

**已确认并授权实施：** 围绕“AI 能准确找回用户所需资料”组织下一轮工作。整理不是只给文件起名、打标签或生成摘要，而是持续建立可检索、可定位、可核验的底稿。详细阶段、责任模块、数据与接口、成本及验收见[AI 整理与准确检索实施蓝图](AI整理与准确检索实施蓝图.md)。

#### 10.9.1 完整底稿与两档预处理

基础索引尽量覆盖支持范围内的全文、结构和来源位置，原件/原文与 AI 摘要、识别、检索词及人工信息分开。快速整理和深入建档共用底稿，不能为了低档位主动省略文件尾部、工作表、章节或成员的索引。AI 可以在单次预算内优先阅读一部分并保留缺口；这种阅读范围不能冒充全文覆盖。

资料的待整理/已整理状态、整理方案状态、基础覆盖和 AI 理解范围分别表达。用户确认后可先入库，后续处理继续；“已整理”“有卡片”或“有来源 ID”均不等于已全面理解，更不等于所有判断正确。

#### 10.9.2 持久处理与大文件

TeamHub 负责持久任务、分块结果、进度、版本权限、租约与成本；Hermes 负责对话和工具策略；模型负责理解与相关性判断；Skill 提供方法。任务按固定版本、generation 和资料库绑定提交，取消、换版和切库后的旧结果不能污染当前索引。

目标是按页、章节、工作表行块或成员有界处理并持续保存，单次预算可控、达到预算可续做，不以原文件大小一刀切丢弃整份整理成果。解析器现有整文件字节及其他安全上限尚未全部解除；持久片段不等于已经实现全格式流式解析或精确断点续读。保留安全限制，并以阶段改造验证目标。

表格片段保留表头、单位和对象，文字保留章节，PDF 保留实际页，集合保留父版本、成员相对路径和成员内位置；图像识别覆盖单列。文字可提取不能证明页面图形已理解，成员清单不能证明成员正文已处理。

#### 10.9.3 检索、证据与实施状态

R1 已实现持久片段、幂等分批发布与重启续跑、旧索引兼容回填、当前版本隔离、多词相关性排序及具体命中位置，并接入伙伴和界面。续跑范围是解析产物落盘后的片段发布，尚未覆盖解析器内部检查点。检索按关键词覆盖和来源加权，不是向量语义检索；详见[第一阶段验收](../reviews/AI整理与准确检索第一阶段验收-2026-10-23.md)。

后续在同一权限和版本范围内接入真实 Embedding 语义召回，与词法结果采用 RRF 融合，按需要重排，最终回到原文核验。真实 Embedding、全格式大文件续处理、全库自动视觉识别均未由本轮规划直接完成，不将关键词工具改写查询称为已具备向量语义检索。

来源存在只能证明位置可追溯；结论是否正确还需检查上下文、对象、单位、限制条件和版本。默认私有，片段、摘要、向量及缓存继承来源权限；本机检索不依赖组织云端，生成索引不等于授权外发或自动共享。

#### 10.9.4 验证方式

以真实回找问题和已知相关资料建立基线，固定版本、方法及预算，分别观察前 5/10 召回、前 5/10 精度、版本混淆、定位与事实支持、延迟和成本；覆盖同义词、精确位号、表格末尾、图片/图示、成员及无答案场景。解析覆盖和检索质量分别统计，不能用较好的摘要掩盖漏读，也不承诺任何大小或所有问题都能 100% 找回。

### 11.3 建议的最小观察维度

- 从开始查找到辨认资料的时间、尝试次数，以及是否仍依赖问人。
- 没找到是因为未收录、无权限、标签缺失，还是筛选排除了目标。
- 使用者如何选择总览、分类和收藏，是否误解移出分类、取消收藏与删除。
- 不解释“绑定”概念时，成员能否直接进入和切换资料库，能否清楚分辨当前浏览库、新发布目标与原资料更新位置。
- 标签补充时机、成本、放弃原因，以及对他人的实际帮助。
- AI 预整理建议是否减少填写和返工，用户能否区分“AI 已预整理”“索引已建立”和“已进入文档库”；采用率和整理总耗时见 §4.9 的后续验证。
- 能否辨认确切版本，理解本地编辑与远端更新的边界。
- 能否区分“恢复本地历史”“接收云端更新”和“提交共享新版本”；两端编号不同、未保存修改受保护、重复更新及并发冲突时，能否理解实际结果。该项对应 §8.7—8.9 的后续实现与试用验证。
- 本地删除或成员退出后，共享资料是否仍按权限可用。
- 接收者能否凭提醒找到收到的资料，理解未读、已撤回与本地已收录的区别；指定权限、管理员授权和撤回是否符合实际协作预期。
- 路径迁移和恢复是否可理解、可核对，而不仅是按钮返回成功。

这些是验证建议，不是已经批准或开启的用户行为采集方案。

3. 原则变化同步正文、D/Q 台账、范围、验证假设及变更记录；不继续堆“补充共识”孤立段。
4. 接口字段和排期进入专题文档；基石保留含义、理由与边界。
5. 区分实现成功、测试通过和真实用户受益。
6. 考虑扩展性不等于预先实现延期能力。
7. 工程默认可按证据调整，但不能无声改变产品原则；旧代码不覆盖新共识。
8. 修改后检查独立读者能否解释对象、状态、分类、收藏、共享及物理位置，避免作者依赖会话才能读懂。

### B.3 历史能力不自动形成产品承诺

早期代码中已有 `move / copy / index`、本地与云端多种状态字段、变更日志和手动推送等机制。当时界面对文件夹推送、拉取也有禁用限制。这些都是历史观察，不表示当前产品承诺完整保留或扩展每一项。

尤其需要注意：追加新版本并保留旧版现已成为已确认原则；不可变存储布局、文件托管边界、发布完整性和幂等处理的具体机制，是为满足原则提出的可靠性方案。两者不能混淆，也不能因旧代码已有同名字段就认为已实现目标。

## 附录 C. 术语与参考

### C.1 术语约定

| 术语 | 含义 |
| --- | --- |
| 资料对象 | 具有稳定身份、标签和版本关联的管理单元 |
| 整体文件夹资料 | 一套文件作为一个资料对象，整体保存快照 |
| 分类文件夹 | 已整理资料的类别入口，当前对应实际存放目录 |
| 全部资料 | 本地已整理资料总览，不等于全部磁盘文件或云端总库 |
| 本地收藏 | 指向已整理资料的快捷引用，不复制内容 |
| 共享收藏 | 指向远端资料的引用，未必已经取回本地，访问受远端权限控制 |
| 待整理 | 已登记、待完善整理信息的状态及工作区域 |
| 已整理 | 已完成个人整理的使用状态，不等于内容已获批准 |
| 文件库 / 待整理路径 | 两个可独立配置的物理区域，不以包含关系推断归属 |
| 元数据登记 | 记录身份、区域、位置及关联；从收录时开始 |
| 内容快照 | 某一版本确定的内容，与可编辑工作副本区分 |
| 当前版本 | 所属资料对象当前选定的已保存版本；工作文件仍可能有未保存修改，编号也不一定最大 |
| 恢复本地版本 | 切换到已有本地历史，恢复本身不新增内容版本，不改变云端 |
| 更新本地 | 主动接收关联共享资料的目标版本；不同内容新增本地接收版本，保留原有历史，重复规则见 §8.8 |
| 取回到 TeamHub | 将共享资料纳入个人管理并记录来源；不同于普通浏览器下载 |
| 提交共享新版本 | 在已有共享资料上明确追加版本，经过权限及基准检查；不自动上传全部本地历史 |
| 提交基准 | 成功接收、提交或显式处理冲突后确认的共享版本，用于防止未察觉的并发覆盖；不等同于仅浏览到的云端当前版本 |
| 覆盖共享 | 历史说法，实际为追加版本并保留旧版 |
| 自由标签 | 可按理解补充的关系线索，不强制完整分类树 |
| 标签共享 | 在共享范围内公开并共同维护资料与标签的关联 |
| 候选集合 | 筛选后供人工辨认目标的一组资料，不要求唯一结果 |
| 个人区 | 个人资料管理范围，默认私有 |
| 共享区 | 主动发布后按组织权限可发现、获取的资料范围 |
| 指定成员共享 | 对资料授予明确成员访问权，不因同空间或管理员身份自动可读 |
| 资料投递 | 主动发送确定内容并形成收发记录的独立功能，提醒不等于本地收录 |
| 投递撤回 | 终止本次投递相应访问资格；不同于组织资料删除，也不收回独立保存的个人副本 |
| 投递附件 | 一次发送固定的内容快照及独立引用；其权限不自动覆盖源资料其他版本 |
| 资料管理者 | 对特定资料管理授权的候选资源角色，区别于组织管理员；具体方案见 Q-18 |
| 双标签 | 同一共享资料同时拥有公共标注和个人私有标注的候选能力，延期 |
| 组织归属 | 共同使用、存续与控制的产品方向，不是法律产权认定 |
| 云端 / 共享服务端 | 服务端角色，可以同机模拟或内网部署，不必是公有云 |
| API 解耦 | 通过接口通信，独立保存和运行；仍须兼容协议与业务语义 |
| MVP | 以较小范围验证核心流程和价值，不能忽略正确性与权限 |
