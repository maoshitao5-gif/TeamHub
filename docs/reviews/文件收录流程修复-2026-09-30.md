# 文件夹首次收录失败：排查与修复

日期：2026-09-30。

## 已确认的事实与证据边界

桌面后端访问日志中出现两组 quick-add 首次 HTTP 500、再次 HTTP 200。旧的文件操作补偿逻辑把底层异常转为通用 HTTP 错误，没有记录原始异常栈，因此无法仅凭旧日志确定这两次错误的确切原因。

合成的 45 MiB 文件夹在原打包后端首次收录成功，未复现稳定的打包或初始化故障。受控测试复现了“首次捕获期间源文件发生一次变化”的失败路径；修复后同一个收录请求可完成。该复现证明修复有效，不等于已经确认用户原事件由此导致。

## 本轮修改

- 将文件夹捕获期间的变化单独分类，最多完整捕获三次，间隔 0.2 / 0.4 秒。每次失败清理暂存，下一次仍执行完整一致性校验；不放宽哈希或变更检测。
- 只重试捕获，不重放文件移动和数据库提交。权限、损坏对象等其他失败不自动重试。
- 持续变化返回明确的 HTTP 409，原位置与事务按原有规则回滚；异常栈写入日志。
- 收录请求不再受普通查询的 30 秒超时限制，界面显示正在校验收录并防止重复点击。
- 收录错误由页面统一显示一次，网络异常同样遵守静默错误配置。

## 验证

- 后端 173 项通过：受限环境 159 项通过，其余 14 项因本机端口权限未执行，允许端口后单独补跑全部通过。
- 新增三项回归：首次短暂变化后成功且仅一版；持续变化停止且源文件仍在；权限错误不重试。
- 界面临时库验收通过：选择取消、单文件、整体文件夹收录，以及既有收藏和分类流程。
- 前端构建、后端打包完成。验收使用隔离资料库，未对用户的原文件执行收录测试。

## 尚需确认

用户用原先失败的文件夹重新尝试一次。如果仍失败，新版日志可保留底层异常，进一步定位，而不再只剩通用 HTTP 500。
