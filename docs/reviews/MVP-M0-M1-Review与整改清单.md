## 4. M0 详细意见

### M0-R01：沙箱配置隔离不完整

**位置：** [启动脚本](../../scripts/mvp-dev.sh) 的 `start()`；[本地配置](../../backend/app/config.py)；[共享配置](../../cloud_backend/app/config.py)。

**发现与证据：**

- 本地后端仅改变工作目录，配置加载仍会搜索 `.env`、`../.env`、`../../.env`，并继承进程环境变量。
- 在临时项目目录的上级 `.env` 中设置 `LIBRARY_PATH` 后，从模拟沙箱目录加载实际配置并初始化数据库，数据库成功写入沙箱外的模拟资料库。复现结果：`ESCAPED_SANDBOX=True`、`DB_CREATED=True`。该目标仍位于审查者创建的临时目录内。
- 共享端显式覆盖 `DATABASE_URL` 只隔离了数据库地址，仍会读取其他 `.env` 设置。配置级复现结果为 `ENV_STILL_READ=True`。共享应用还保留后台 OSS 初始化逻辑，因此脚本中“不读真实 .env”的注释不成立。本次没有实际访问真实外部存储。

**影响：** 沙箱位置不能保证数据和外部服务隔离，开发启动可能使用真实资料库或真实服务配置。

**整改建议：** 提供明确的开发沙箱配置入口，控制配置文件来源和环境变量继承；显式指定个人库、共享库及相关运行目录，关闭沙箱不需要的外部初始化。初始化前校验实际解析出的数据路径确实位于预期范围。不能仅通过修改注释宣告隔离完成。

**复验标准：**

- 上级 `.env` 和继承环境变量分别指向沙箱外的临时“诱饵目录”时，启动仍使用沙箱配置，或明确拒绝启动。
- 诱饵目录没有生成或修改数据库、资料及配置文件。
- 共享端不会因真实默认配置而触发外部存储初始化；所有后端实际数据位置可核对。

### M0-R02：停止脚本可能终止无关进程

**位置：** [启动脚本](../../scripts/mvp-dev.sh) 的 `stop()`。

**发现与证据：** 目前仅核对 PID 对应进程名称是否包含 `python` 或 `uvicorn`。将审查者自行启动的无关 Python 测试进程 PID 写入临时 PID 文件，模拟过期记录或 PID 被复用后，原停止逻辑确实终止了该进程，退出信号为 SIGTERM。没有终止用户的真实进程。

**影响：** PID 文件和进程名称不足以证明进程属于本脚本，可能影响其他开发任务。

**整改建议：** 记录并核验进程身份，除 PID 外结合启动时间、预期命令与本次运行标识等信息；必要时采用可靠的进程管理方式。归属无法确认时不发送终止信号，并说明记录已失效。停止后确认目标已退出，再清理状态。

**复验标准：** 自己启动的服务能够停止；不存在的 PID、失效记录、指向无关 Python 进程的记录均不会伤及其他进程；重复停止结果明确且安全。

### M0-R03：启动失败仍返回成功

**位置：** [启动脚本](../../scripts/mvp-dev.sh) 的 `start()`。

**发现与证据：** 在临时目录复制原脚本，用立即返回错误码 42 的测试可执行文件代替两个 Python 入口，脚本仍返回 0 并打印两条“已启动”。当前流程没有等待健康就绪或检查子进程提前退出。

**影响：** 人工或自动化流程会在服务不可用时继续执行；一个服务成功、另一个失败时还可能遗留半启动状态。

**整改建议：** 启动后执行有超时的进程存活与健康检查，确认成功后再报告就绪。任何一个必要服务失败时，返回非零状态，提供日志位置，并只清理本次启动创建的进程。该清理依赖 M0-R02 的归属保障。

**复验标准：** 正常启动成功；子进程立即失败、一个后端失败、健康检查超时均如实报错；失败后没有本次遗留进程；不终止启动前已存在的服务。

### M0-R04：界面启动验收证据缺失

**位置：** [验证记录](MVP验证记录.md) 的 M0 退出条件核对；[蓝图](../product/TeamHub-MVP实施蓝图.md) 的 M0 退出条件。

**发现与证据：** 记录明确写了“后端已验证；前端构建通过，界面联调留待 M4+”，但同时宣告 M0 完成。构建成功不能证明界面能够启动。

**影响：** 尚未确认开发者能进入实际界面，基础连接问题可能延迟暴露。

**整改建议：** 用隔离环境启动计划用于后续开发的界面，验证页面基本呈现及对本地后端的基础请求；分别确认共享后端健康状态。不要求提前实现发布、下载等完整业务流程。如果仅验证浏览器开发界面，应明确 Electron 桌面壳尚未验证，不混称为全部启动通过。

**复验标准：** 记录实际启动方式、界面类型、运行结果、基础请求结果及未覆盖内容；将构建结果与运行结果分开描述。

## 5. M1 详细意见

### M1-R01：个人库版本约束未完整落地

**位置：** [个人库模型](../../backend/app/models.py) 的 `Document` / `Version`；[个人库迁移](../../backend/app/core/migrations.py)。

**发现与证据：** 在按当前模型建立的临时空库中，同一资料插入两条 `version_number=1` 的版本并提交成功；资料的 `current_version_id` 设置为不存在的版本 ID 也提交成功。

复现结果：`local_duplicate_version_number_accepted=true`、`dangling_current_version_accepted=true`。

**影响：** 后续接口无法依赖数据库保证版本号唯一；当前版本引用可能悬空。契约中的“数据库约束”和“唯一当前版本来源”尚未成为可靠实现。

**整改建议：**

- 在模型和旧库迁移中同时落实 `(document_id, version_number)` 唯一约束，不能只改空库建表路径。
- 为当前版本引用建立存在性与归属校验；仅添加普通版本外键仍不足以防止引用其他资料的版本。
- 未建立首个版本时是否允许空引用要明确；迁移后禁止非法的非空引用。
- 明确旧 `is_current` 的读写过渡安排，避免两套当前版本来源独立更新。处理旧数据冲突后再建立约束，不直接删除冲突记录。

**复验标准：** 空库与迁移库都拒绝同资料重复版本号；不同资料可以使用相同版本号和内容哈希；不存在或属于其他资料的当前版本不能通过受支持的写入路径落库；正常当前版本绑定成功。

### M1-R02：旧共享写入入口没有彻底收敛

**位置：** [共享路由注册](../../cloud_backend/app/api/router.py)；[共享资料接口](../../cloud_backend/app/api/documents.py) 的 `push_document()` / `create_version_snapshot()`。

**发现与证据：** 使用临时共享库和普通成员身份，在应用层调用：

- `POST /api/workspaces/{ws_id}/documents/{doc_id}/push` 返回 **200**，创建资料及一条版本，但 `current_version_id` 为 `NULL`。
- 随后调用该资料的旧 `versions/snapshot` 接口，返回 **500**。旧实现复制相同版本号，与 M1 新增的唯一约束冲突。

该复现通过进程内 TestClient 完成，没有连接真实共享服务。

**影响：** 即使停用了 `/sync/**` 和设备 manifest 入口，保留的旧写入仍能产生不符合新契约的组织数据，并导致新旧规则冲突。

**整改建议：** 在 M1 停用这类旧写入入口，返回明确的 410 契约。可以保留必要只读接口；如确有兼容写入需求，必须通过唯一的新业务入口执行完整约束。新发布能力属于 M4，M1 可以暂不提供，不能以等待 M4 为由继续开放不符合规则的旧写入。

**复验标准：** 上述旧入口及同类可替代入口无法再写入组织数据；验证响应之外，还核对资料、版本、标签关联和变更记录未新增或修改。只读能力按保留范围正常工作。

### M1-R03：迁移无法处理旧数据的版本号冲突

**位置：** [共享迁移 004](../../cloud_backend/alembic/versions/004_mvp_contract.py) 的 `uq_cloud_version_doc_num` 创建步骤；同时涉及个人库迁移策略。

**发现与证据：** 在旧 schema 副本中构造旧模型允许的同资料、同版本号记录，包括带子文件路径的记录，执行 003→004 时直接触发：

```text
IntegrityError: UNIQUE constraint failed:
cloud_versions.document_id, cloud_versions.version_number
```

现有迁移测试只使用版本号不冲突的简化样本，未覆盖旧文件夹子文件记录或旧快照形成的重复号。

**影响：** 有效旧数据可能无法升级；旧“子文件版本”不能直接等同于新“整份资料版本”。唯一索引创建失败也不能代替可理解的迁移异常报告。

**整改建议：**

- 建立约束前检查重复版本号、多条当前标记及子文件版本，区分可转换数据与无法确认的历史。
- 对可以可靠转换的记录明确映射规则；对无法可靠还原的记录保留原始数据并报告异常，不伪造完整历史，不简单删行或任意重编号。
- M1 至少交付明确策略及构造副本验证；不要求提前完成 M6 的真实资产迁移演练。
- 验证失败后的数据库状态和重试方式，避免部分结构已改变却无法重跑。

**复验标准：** 正常旧库迁移成功；含重复号及子文件记录的副本能够按策略转换，或在可恢复状态下给出明确异常；数据数量与映射可核对；重复执行不会丢失数据或重复建立结构；原库不被改写。

### M1-R04：切库未协调在途会话和任务

**位置：** [数据库生命周期](../../backend/app/database.py) 的 `rebind_engine()`；[切库接口](../../backend/app/api/settings_api.py) 的 `setup_library()`。

**发现与证据：** 持有 A 库会话并执行查询后，切换设置、重建引擎并初始化 B 库，原 A 库会话仍可提交新增记录。复现结果：`old_session_can_write_A_after_switch_to_B=true`。

`engine.dispose()` 处理连接池，并不等于终止所有正在使用的会话或后台任务。现有切库测试先关闭 A 会话再切换，只证明后续新建会话绑定 B 库；测试中的再次调用 `dispose()` 也不能证明在途连接已停止。

**影响：** 切库返回后仍可能有旧任务向 A 写入；同时，全局配置已指向 B，存在数据库与文件路径使用不同库上下文的风险。此次直接复现的是“切库后仍能写 A”，未宣称已经复现跨库文件损坏。

**整改建议：** 建立最小切库协调流程：阻止新的冲突操作进入，等待已有操作安全结束或明确取消任务，关闭相关会话，再切换配置和引擎。若暂不支持运行中切换，可检测忙碌状态并明确拒绝。单次操作应使用稳定的库上下文，不在执行中混用变化后的全局路径。

**复验标准：** 有在途写入或后台任务时，切库按设计等待、取消或拒绝；成功返回后不再有属于旧库的在途写入；新操作只写 B，A 的最终状态符合切换前已完成操作；初始化失败时不遗留配置与数据库不一致的状态。

## 6. 整改顺序与验证范围

建议执行顺序：

1. **修复 M0-R01、M0-R02：** 先保证整改与测试环境不会触碰错误的数据和进程。
2. **修复 M0-R03，补齐 M0-R04：** 完成可用、可核验的启动基线。
3. **关闭 M1-R02 的旧写入入口：** 防止继续产生新旧语义混杂的数据。
4. **联合处理 M1-R03、M1-R01：** 先明确旧数据转换，再落实空库与迁移库一致的约束。
5. **修复 M1-R04：** 完成切库生命周期协调。
6. **更新证据和阶段状态：** 按问题编号逐项复验，再更新蓝图及验证记录中的完成结论。

不要求扩大到全项目压测、全平台测试、M2 快照实现或 M4 完整发布流程。新增测试应覆盖本文件中的实际失败行为，避免仅重复实现细节。
