# AI 预整理与用户确认验收

开始日期：2026-10-20；完成日期：2026-10-21。

结论：本轮代码、独立复核、隔离测试和 macOS ARM64 桌面交付已完成。资料在待整理中由 AI 准备名称、标签和分类方案，用户查看、调整并一次确认后才进入文档库；支持四状态、批量审阅、失败处理和撤销整理。根目录启动入口已优先选择本轮新包。

依据：[项目基石 §4.9](../product/TeamHub项目基石.md#foundation-ai-preorganize)、[产品方案](../product/AI预整理与用户确认产品方案.md)、[实施蓝图](../product/AI预整理实施蓝图.md)。操作见[使用指引](../guides/AI预整理使用指引.md)。

## 1. 已交付的使用流程

1. 收录后仍进入待整理。仅配置 AI 密钥不会触发后台外发。
2. 用户选择一批资料启动 AI 预整理，或主动开启当前库的自动预整理；一次说明范围和目标服务，不逐文件、逐工具确认。
3. 后台根据各份资料的已保存版本准备方案，显示待处理、处理中、已预整理待确认、失败四种状态。
4. 用户可单份或批量审阅，修改建议名称、标签和可选分类目录，一次确认采用。
5. TeamHub 执行改名、关联标签、归入目录和文档库，不增加内容版本。最近整理记录提供撤销入口。

标签至少一个，分类目录可留空。未准备好、失败或不使用 AI 的资料，均可继续手工整理。批量采用按份返回结果，失败项保留输入，已成功项不重复执行。后台轮询不会覆盖审阅中的人工修改，手工批量整理也固定打开窗口时选中的对象。

## 2. 架构与一致性

| 层次 | 本轮职责 |
| --- | --- |
| 待整理页面 | 状态筛选、批次启动、当前库开关、可编辑方案、一次采用、最近整理与撤销 |
| 预整理服务 | 队列、范围授权、版本与元数据守卫、方案存储、幂等、按份采用和撤销 |
| Hermes | 在独立预整理任务中阅读目标资料，提交结构化 `propose_organization` 结果 |
| TeamHub 阅读工具 | 固定版本的文字、表格、原页或图片读取，登记真实来源及处理缺口 |
| 既有资料管理 | 正式文档身份、内容快照、文件移动与失败回滚 |

新增 `preorganize_policy`、`preorganize_proposals`、`preorganize_requests`、`preorganize_operations` 表；原数据库保留，新表随正常初始化创建。接口统一位于 `/api/ai/preorganize`，详见实施蓝图与[接口契约 §10.12](../architecture/MVP数据与接口契约.md#contract-ai-preorganize)。

普通聊天仍使用原生会话和原工具集。预整理不生成可见聊天会话，不携带其他对话历史；只读当前目标资料，分类语境限于有界的已有标签和目录名称。合法结构化方案提交即结束，避免为了再总结一次而增加请求。Hermes 适配器修订为 **3**；固定上游 **v0.22.2** 源码未修改。

后台单并发并与交互任务协调，优先让聊天取得通道。服务变更、切库、取消、手工整理、版本或管理信息变化均参与失效判断。取消、失败和中断任务不自动重放可能已收费的请求；明确重试由用户发起。自动模式关闭只撤销该模式的任务，不误伤用户主动发起的批次。

确认采用前还检查实际工作文件内容，避免把旧版本建议应用到已修改的文件。每份采用在数据库写事务内完成，记录整理前后状态；同一请求编号及相同内容不会重复采用。撤销核验后续名称、标签、位置、工作内容和原位置占用，原标签被删除或身份改变也拒绝静默恢复。

## 3. 独立审查与修复

通用代码、Python、JavaScript 及安全审查均已完成，最终复核未留下 P1/P2 问题。主要发现及修复如下：

| 发现 | 修复与验证 |
| --- | --- |
| 图片已成功读取但被缩放时，方案可能遗漏工具给出的处理说明 | 宿主收集视觉工具说明；大尺寸 PNG、PDF 页面及 Office 内嵌图片三类用例先失败后通过 |
| 手工批量窗口使用实时选择，轮询使资料离开当前筛选后可能改变操作对象 | 打开窗口时固定资料 ID 和名称；五项前端回归先失败后通过 |
| 自动任务转为用户主动任务后，关闭自动模式可能按过期缓存误取消 | 在事务中按库、资料、方案和 generation 确定实际撤销对象，仅取消精确匹配的运行任务 |
| 最后一次服务检查与结果提交之间仍有配置变更窗口 | 提交时在同一配置锁与数据库事务中复核并写入；已生成的有效方案仍允许离线采用，不因后来的服务修改被误删 |

以上修复均加入回归测试。其他验证覆盖过期响应、切库、源内容变化、重复采用、部分失败、撤销冲突、本机访问限制与无依据方案拒绝。

## 6. 能力边界与试用评价

本轮按单文件处理，整体收录的文件夹仍需手工整理，或分别收录其中的文件。图像理解取决于所选模型的多模态能力；Hermes 本身不会让纯文字模型获得视觉能力。

预整理方案、原文索引和资料生命周期相互独立。方案有真实读取依据及缺口说明，但“已预整理”不代表全文读取完毕或建立了全面索引。用户确认的标签和名称进入正式资料管理；方案摘要不会冒充原文。

本轮不实现跳过最终确认的自动入库、自动学习全部个人偏好、新建完整目录体系、文件合并或正文改写。文件移动复用现有的进程内回滚机制，尚未新增跨文件系统与 SQLite 的断电恢复日志；数据库事务不等于两种存储的崩溃原子性。

工程测试使用真实 Hermes 与本机模拟模型，验证流程、边界和异常恢复。命名是否合适、标签是否有助查找、分类是否减少操作，仍要用日常资料评价；测试数量不能证明与官方模型产品的体验相同。后续重点观察方案采用率、每份调整量、完成整理耗时、错误原因及实际调用成本。
