# TeamHub 系统级测试与启动修复报告

日期：2026-10-13。用户反馈：双击根目录 `启动本地测试.command`，系统未正常启动。本轮已修复原入口、更新其实际使用的默认桌面包，并完成本地、云端、桌面、网页与打包产物验证。

## 1. 启动诊断与修复

### Finder与Terminal入口补验

用户随后提供的系统截图显示：Finder拒绝打开Terminal，因为Terminal不响应；此时 `.command` 脚本尚未执行。先前执行脚本的测试未覆盖这一关联程序环节，不能用脚本通过结果证明该机器的Finder双击路径正常。

因此新增根目录 `启动TeamHub.app`，通过AppleScript applet的 `do shell script` 直接调用现有启动器，不调用Terminal，也未强制结束用户终端。路径按应用所在目录计算并引用；生成包重新完成本机签名，错误弹框最多等待15秒，日志保留。源码为 `scripts/desktop-launcher.applescript`、构建命令为 `npm run launcher:build`。

实际通过macOS LaunchServices打开最终生成应用，使用临时库与污染环境，验证首启、重复打开复用、后端自动重启身份更新和再次打开全部通过。证据见 `/private/tmp/teamhub-1013-finder-launcher.log`。此轮仅修改启动外壳并复验相关路径，业务模块未改，不将此前371项完整测试称作本次重新执行的结果。

### 1.1 实际入口与环境

原入口固定打开 `dist-electron/mac-arm64/TeamHub.app`，该包来自10月5日；10月7日的优化包位于audit目录，未被原入口使用。原脚本只根据macOS `open` 返回码报告“已请求打开”，没有验证界面或个人后端。

通过真实macOS LaunchServices路径复现：继承 `ELECTRON_RUN_AS_NODE=1` 时，`open` 返回0，但桌面未创建窗口；进程将Chrome启动参数解释为Node参数并报 `bad option`。清除该变量后同一个旧包能正常创建窗口，故不把“旧包”或签名校验问题单独认定为用户无法启动的唯一原因。用户当时Finder/Terminal会话的全部环境无法追溯，本轮修复覆盖这一已复现失败条件及原入口的假成功问题。

改动：

- `scripts/launch-desktop.cjs`：利用桌面自带Node运行，不新增外部Node依赖；GUI进程清除Node模式，捕获启动日志，等待真实就绪。
- `electron/main.js`：界面挂载后原子写入 `desktop-state.json`，记录桌面PID、后端PID、端口与实例标识；窗口关闭、重开、后端重启和退出时维护状态。
- `electron/backend-manager.js`：每次后端就绪通知主进程更新身份。
- `scripts/mvp-dev.sh`：一键入口只有在进程路径、父子归属、实例健康和窗口就绪均通过后才报告成功；处理中文路径的进程检查采用UTF-8。
- `启动本地测试.command`：失败提示指向 `.mvp-sandbox/logs-desktop.log`。

健康探测具有绝对1秒截止，避免持续分块响应使40秒启动等待和启动锁无限挂起。独立审查发现的隐藏窗口重启状态问题已修复。

### 1.2 默认桌面产物

从当前源码重建个人后端与前端，将新桌面包补全本机ad-hoc签名并验证；保留旧包后安装到原路径 `dist-electron/mac-arm64/TeamHub.app`。没有要求用户换入口或去另一个audit目录启动。

旧包保留于 `.mvp-sandbox/backups/2026-10-13-desktop-before-rebuild/TeamHub.app`，同目录manifest记录安装来源。新默认包 `codesign --verify --deep --strict` 通过；这是macOS ARM64本机测试包，未作Apple发行签名或公证。

## 2. 本机云服务恢复

原9000服务自9月29日起持续运行：健康接口200，现行 `/api/server-info` 返回404。其数据库无Alembic标记，15张表全为空、无受管对象，但结构混合了不同阶段。直接在副本执行升级报 `duplicate column name: is_superuser`，未对原库盲目升级或标记revision。

处理过程：

1. 在线一致备份，副本验证失败后保留原进程与数据库。
2. 独立建立005候选库，验证初始化、检查命令、健康、服务身份、云网页及管理网页。
3. 重新核验原PID、启动时间与准确命令，仅停止该已登记云进程。
4. 停写后再确认所有业务表为空、无对象，保存原DB/WAL/SHM和一致快照，再安装经过验证的空005库。
5. 用现有启动器恢复9000服务，跨工具调用确认持续运行。

最终 `/api/health`、`/api/server-info`、`/cloud.html`、`/admin.html` 均200；schema005、protocol1。没有创建试用账号、重置密码或删除旧数据库。原文件、哈希、步骤时间和回退路径见 `.mvp-sandbox/backups/2026-10-13-cloud-before-upgrade/manifest.json`；一致回退快照为其 `stopped-original/cloud.db`。
