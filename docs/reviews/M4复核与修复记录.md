# M4 复核与修复记录

日期：2026-09-28。依据：《TeamHub-MVP实施蓝图》M4、V-05、V-07—V-09 与 V-13 的共享会话部分。

## 1. 结论与范围

本轮已修复发布、取回、共享版本提交及会话处理的主要缺陷，完成定向测试和隔离 Electron 界面验收。M4 核心流程可继续进入后续阶段复核。这里的“通过”指下述已验证范围，不代表生产部署、全部旧资产兼容或 M5/M6 已重新验收。

原来的测试把顺序提交旧基准当作“并发”，没有覆盖真实同时提交；仅测基础取回，也没有证明下载校验与失败清理可靠。新增复现用例先发现：未确认发布仍成功、他人上传可被消费、描述变化不触发幂等冲突、同时提交不能保证一个成功一个冲突。原复现日志位于 `/tmp/teamhub-m4-before.log`（临时证据，不是长期归档）。

## 2. 主要问题与修复

| 问题 | 原影响 | 修复 |
| --- | --- | --- |
| 发布失败结果可能仍写入 ShareLink | 查重等失败被误记为“已共享” | 必须 status=succeeded 且资料/版本 ID 完整，才提交本地关联；查重返回 409 和既有资料入口 |
| 只有前端点击行为，没有服务端确认门槛 | 后台旧调用可直接发布 | 个人适配层和共享端均要求 confirmed=true；界面先展示范围、标签、内容统计和文件夹排除规则 |
| 上传只检查空间，不检查上传者 | 同空间成员可消费他人暂存 | 先核对空间与上传者，越权统一 404；上传 ID 严格按 UUID 定位 |
| 文件夹使用 ZIP 字节摘要充当内容身份 | 不能验证整体内容或正确区分归档与清单 | 服务端检查 ZIP 路径/类型/限额，流式重建规范化清单；content_hash 保存清单摘要，manifest_hash 保存 ZIP 摘要 |
| 幂等负载遗漏描述、操作及目标等字段 | 同编号不同意图可能返回错误旧结果 | 请求摘要包含操作、目标、基准、描述、文件名、标签、内容与归档摘要、另建选择；上传票据可替换以支持重传 |
| 基准检查和写版本之间存在竞态 | 同一基准同时提交可能 500 或不可靠覆盖 | 当前 SQLite 方案在状态读取前 BEGIN IMMEDIATE；并发写入序列化，败者得到 STALE_BASE_VERSION |
| 新版本改写旧 is_current 列 | 历史记录被更新，两个当前来源易漂移 | 历史列不再改写，所有相关读取响应从 current_version_id 推导当前标记 |
| 共享提交未变内容仍追加版本 | 产生无意义重复历史 | 返回 CONTENT_UNCHANGED，沿用当前版并记录本请求的幂等结果 |
| 服务器成功、本地未收到响应 | 重试可能换内容或重复建档 | 本地持久化请求日志，冻结对象、目标、基准和负载；同编号重试沿用原内容，服务端返回同一结果 |
| 取回使用最大版本号、未校验字节 | 当前版判断错误或损坏内容落库 | 默认按 current_version_id 选择；下载先暂存，校验摘要与长度，文件夹再验证整体清单 |
| 取回路径/文件名未严格限制 | 可越界写入、触碰管理目录 | 目标必须在库内工作目录，拒绝危险文件名；排他创建，同名另取新位置 |
| 解包或数据库失败留下部分文件 | 用户看到半份资料、再次取回混入旧内容 | 私有暂存目录自动清理，数据库回滚并移除本次新建工作副本；已有内容不覆盖 |
| 当前服务器与 ShareLink 来源未核对 | 更新可能发送到另一个服务器 | 更新前检查来源服务器，切错服务器时明确 409 |
| 并发 401 各自续期、写回整份旧配置 | 令牌轮换冲突、覆盖新配置或账号混用 | 续期合并，合并写令牌字段；退出、换账号、切库后不复活或串写旧会话 |
| 文件夹菜单被禁用、没有更新/另建操作入口 | API 存在但用户无法完成流程 | 启用文件夹共享，确认窗提供更新原资料/另建资料与失败反馈；请求编号在会话中保留供重试 |

## 3. 请求与存储规则

### 3.1 发布与重试

首次发布上传**当前已保存版本**；外部工作文件未保存的修改不自动混入首次发布。更新原资料由用户明确确认，先保存当前工作内容再提交；原组织标签不被整组替换。另建资料显式 force_new=true，可以复用同一内容对象，但生成新的共享资料 ID。

本地日志存于 `<个人库>/.teamhub/publications/<身份与请求摘要>.json`，包含服务器、空间、操作者、请求编号、冻结负载、对象路径和结果，不存令牌。日志在网络提交前落盘；本地关联提交成功后标记 applied。已完成请求再次调用不会把本地关联倒退到旧共享版本。客户端保持同一 request_id 是重试前提；界面使用 sessionStorage 保留未完成编号。

界面刷新可以找回本浏览器会话的请求编号；关闭整个应用后没有新增“未完成发布管理页”，此时可依据本地日志或既有编号重放 API。该限制不等于允许重复发布未确认内容。

### 3.2 文件夹、上传与下载

- 文件夹清单编码与 M3 一致：version="1"，路径排序，记录类型、文件大小和内容 SHA-256；保留空目录及隐藏项，拒绝管理目录、链接、特殊文件、重复/大小写冲突与越界路径。
- 服务端重新校验暂存字节摘要和长度；文件夹另行流式重建清单。普通文件不得声明文件夹归档摘要，防止下载定位与已保存对象错配。
- 上传中断或超限清理本次部分暂存；对象落位采用排他硬链接，既有对象必须校验一致才能复用，不直接覆盖。
- 内容可靠落盘后才提交数据库引用。数据库提交失败保留完整暂存，允许同上传票据重试；提交失败最多遗留未引用对象，不生成指向部分上传的资料。
- 下载服务先核对对象摘要/长度再返回；个人取回端仍独立验证，之后才还原工作位置和保存来源关联。
- 初始限额：上传 3 GiB（UPLOAD_MAX_BYTES），个人取回 3 GiB（SHARED_DOWNLOAD_MAX_BYTES）；文件夹 10,000 条目、单文件 1 GiB、累计展开 2 GiB（与 M3 同名配置）。均需以脱敏真实资料校准。

### 3.3 数据库及性能边界

共享端按已选定的 SQLite 实现写入串行化，数据库锁跨线程和进程生效；当前锁覆盖对象验证及版本提交，保障正确性但可能让大文件提交相互等待。竞争超时返回可重试错误。未声称已支持 PostgreSQL 的并发策略或大规模部署。

## 5. 保留事项与兼容性

1. **暂存、未引用对象及请求日志回收未实施。** 当前保留服务端上传暂存用于提交失败恢复；同内容重传也可能留下额外暂存。试用需关注存储增长，后续回收必须按已完成请求、期限及对象引用安全处理，不能直接按文件年龄删对象。
2. **旧文件夹共享记录不是自动兼容。** 旧实现把 ZIP 摘要写入 content_hash 且缺 manifest_hash；新取回会明确拒绝不完整校验信息。本轮不改写真实旧数据库，应在副本上验证后迁移或重新确认发布。新版本写入不可简单回退旧代码。
3. confirmed、manifest_hash、original_filename 等请求规则已收紧；旧后台调用不能继续无确认发布。后续阶段的联调脚本应明确表示确认意图，不应为保持旧脚本绿色放松门槛。
4. 不宣称进程强杀、断电、真实大文件吞吐、目标服务器文件系统或生产部署已验证。对象落位依赖当前受管目录同卷且支持硬链接。
5. 组织标签权限、管理员回收及备份/打包仍属 M5/M6；本轮只回归直接相关的权限和停用入口，没有以全阶段测试替代 M4 复核。

代码及文档均留在工作区，未提交 Git。安全相关改动按本机 security-review 技能检查上传输入、权限、路径、会话与错误边界；没有据此扩展无关的生产部署或安全整改任务。
