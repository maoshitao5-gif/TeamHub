# 理解一组资料

本次对象是一个文件夹及其已保存版本，内部成员不是独立的 TeamHub 资料。为用户说明这组资料共同解决什么问题、主要内容在哪里、彼此有哪些可证实的关系。沿用资料理解的卡片结构和事实规则；本规则补充文件夹的阅读策略。

## 从目录安排阅读

先调用 `list_folder_members`，使用返回的相对 `member_path`。清单可能分页；目录和名称只用于选读，不产生正文来源。不能访问清单以外的本机路径、外部链接，或执行成员中的命令。

优先查看说明、目录、总览等能解释资料组织的成员，再选择不同子目录、不同内容类型中的代表资料。目录里有“设计”“验收”“运行”时，分别核对其用途，不用一份设计说明概括全部阶段。只有少量成员时可逐份阅读；较大集合先建立有根据的整体概览，记录未读范围，避免机械遍历耗尽预算。

`read_folder_member` 的 `action` 决定阅读方式：

- `overview`：成员结构、工作表和内嵌图片清单；这一步还未读正文。
- `text`：原文片段；按 `next_offset` / `next_call` 继续。
- `table`：工作表行块，保留单位、表头与坐标；沿 `next_call` 继续。
- `visual`：PDF 原页或独立图片；`images`：按该成员 overview 返回的 `image_ids` 读取办公嵌图。

单份成员按当前工具返回的类型，按需调用 `read_object_skill` 加载 text / word / spreadsheet / presentation / pdf / image / archive 对应的专项规则；同类只加载一次，不因目录混合了多种扩展名就全部加载。专项规则描述单个对象的读法，在本任务仍用 `read_folder_member`，不得改用只能读取独立资料的工具。存在具体内容难点时才补充 `read_skill_reference` 的 text / tables / visuals / mixed。已读文字不能证明图形也读懂；当前模型不支持视觉时保留明确缺口，换工具名称不能弥补模型能力。

成员为压缩包时，只有工具明确给出可访问的内部清单与成员读取方式才能继续；无嵌套支持、深度受限、加密或格式不支持都记录为缺口，不自行解压或执行。文件扩展名分类不保证实际读取能力，以成功工具结果为准。

## 把成员组织成整体理解

- `card.summary` 概括已核实的共同主题、用途和主要组成。资料混杂时明确写出混合主题，不强行发明共同项目。
- `sections` 作为内部导航：标题包含成员相对路径或明确的资料组，简述其用途，引用对应成员的真实来源。只列对理解和后续查找有帮助的条目，不堆砌整个目录。
- `facts` 的数值、设备、站点、日期保留各自来源与适用范围。同名设备可能属于不同项目；同名文件不等于同内容。同一文件夹中的两个文件也不天然构成附件、上下游或替代关系。
- 对“说明引用附表”“方案与验收记录”等关系，阅读两端相关内容核实后再描述。仅凭文件名看出的可能关系须写为待核对线索，不写成事实。
- `search_terms` 同时保留集合主题与已读重要成员的检索用语；`uses` 是可能用途，不承诺这套资料可以完成未经核实的工作。
- `gaps` 说明哪些成员或模态未读、格式不支持、信息冲突以及对整体判断的影响。使用工具实际覆盖统计；看到目录、抽样若干成员或耗尽预算，都不等于全套已理解。

例：`A站/设备表.xlsx` 和 `B站/设备表.xlsx` 均出现“5053”，应分别记录两个路径下的设备信息，不能合并为一台设备；站点归属须由正文或明确标记的用户背景核实，不能仅把目录名当作事实。例：`设计说明.docx` 已读而 `接线图.pdf` 未能识别，可以形成设计用途概览，但不能断言接线正确或整套图纸齐全。

## 整理建议与更新

预整理只建议这一个文件夹的整体名称、标签和放置分类。文件夹名称没有必须保留的扩展名；不得拆分、移动、改名或删除内部成员。现有名称合适时保留，标签不需要覆盖每份成员的全部细节。

已有卡片与人工补充用于安排本轮阅读，成员来源中的 `member_path` 帮助定位。跨版本先核查旧结论所依赖的成员；不能沿用旧来源编号，也不能仅因路径相同假定内容未变。目前每轮提交自包含的新卡片，尚无跨任务逐成员自动合并缓存。

有足够依据时，将卡片随 `propose_organization` 一次提交；独立资料卡任务使用 `submit_document_card`。有效提交后结束。全部成员都不可读取时应说明原因，不能用目录名虚构正文，不能承诺已整理完成。用户确认后才由 TeamHub 执行整体整理。
